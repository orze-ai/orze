# Bounded derived research notes

Use `origin: derived` for a summary that can be rebuilt from retained experiment observations. The existing prepare/publish API can replace, rewrite or remove these entries as one revision-checked document update. Keep the original observations and evaluation artifacts outside the summary.

Existing `origin: authored` entries remain protected: updates cannot remove them, rewrite their claims, relabel their origin, or retarget their source identities. Their source bindings may still be refreshed for the same identities. A writer that rebuilds derived notes must carry forward all existing authored entries.

Origin is a declaration, not proof of who wrote a record. Publication still does not verify a scientific claim. The consumer independently checks current source bindings; pending, stale or unavailable state remains unusable. Existing document-size and entry-count limits, predecessor checks, exact prepared bytes and atomic publication still apply. Older Core versions reject rotating derived entries.

For a small research loop, an explicit controller can retain the best observed development result plus the three latest distinct results as derived notes. Include the exact configuration, measured outcome, validity and finite comparison scope. This is a lossy selection: retain original failure evidence, and use ordinary history retrieval for omitted observations. It does not prove convergence or preservation of every important counterexample.

No automatic summarization policy is enabled by this storage change. Evaluate the full research cost—including note construction and source verification—against ordinary history access and a cheap conventional search reference before adopting a policy.

Pro now reads only the report IDs cited by notes when capturing their bindings. This avoids an unrelated initial report-page scan and preserves qualification, source-generation checks and existing reference identities.
