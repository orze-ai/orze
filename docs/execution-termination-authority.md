# 执行停止确认契约（V1-02D1）

本文描述当前开发分支的停止确认边界，不是发布公告，也不代表全部执行生命周期已闭合。Core 提供实现，Pro 使用配对的 Core 行为。

## 范围

覆盖训练器及 posthoc 的受控强制停止、评估器的超时/异常停止、启动后初始化失败、训练进程启动后槽位登记失败，以及相关 shutdown、重试和恢复入口。普通 shutdown 仍允许按既有规则分离运行中的训练任务；这不表示任务已经停止。角色进程沿用已有角色停止协议。

“已请求停止”“主进程已有退出码”和“受控进程组及已跟踪后代已停止”不是同一件事。此切片要求停止器返回值严格为 `True`，且随后观察到的退出码类型严格为 `int`（不接受 `bool`），才能发布停止确认。仅 `None`、真值对象、退出码存在或没有抛异常都不够。

## 持久记录与 HOLD

停止器调用前持久发布请求；停止确认成功后才发布确认。两份记录位于该 idea 的目录中：

```text
_execution_stops/<attempt_id>/requested.json
_execution_stops/<attempt_id>/confirmed.json
```

请求带有 idea、attempt、phase 和随机 nonce；确认绑定请求原始字节的 SHA-256，并记录停止确认和退出码。文件按只创建、不覆盖的方式发布，包含同步和精确读回检查。这是框架内的记录绑定，不是面向恶意文件写入者的签名认证，也不是完整 attempt CAS。

读取使用有界校验：最多 1024 个停止记录目录，单文件最多 8192 字节；拒绝符号链接、非普通文件、多硬链接、非法/缺失记录、不匹配哈希、额外文件、超限和读取失败。不存在整个停止记录目录时保留旧项目兼容；存在空目录或半份记录则不能当作“没有停止请求”。

停止未确认时，产生 `TerminationUnconfirmed` 或保留受控的活动槽位，进入 HOLD：

- 不发布计算终态、不将阶段改回待运行、不执行普通修复重试、不释放 claim。
- 即使随后主进程退出，也不重新猜测先前未确认的写入者已经消失。
- 已持久化的 HOLD 不依赖原进程对象或 active 字典存活；直接 launch、评估旧输出短路、reset、claim、孤儿清理和相应启动恢复路径均需尊重它。
- 评估专用重试不能把 `_execution_stops` 当作普通评估产物移动或归档。

停止器返回 `False` 不触发自动停止重试或重新启动。没有按年龄、PID 消失或控制器重启自动解除 HOLD 的规则；需要先由外部核实不确定执行结果。本切片不提供“删除标记即证明安全”的恢复流程。

## 兼容与限制

旧测试中模拟停止成功但返回 `None` 的替身，需要显式返回 `True` 并提供整数退出码。这是测试夹具迁移，不是放宽生产检查；模拟 `False` 的不确定停止不能因此变为成功。

如果首次停止请求尚未持久化时所有相关存储操作就已失败，可能只留下内存中的 HOLD；尤其启动后初始化失败、进程尚未登记时，不能据此宣称跨重启安全。没有结果目录的旧停止调用同样没有持久化保证。

本切片尚未闭合：

- 普通自然退出时的完整后代进程证明及所有逃逸执行者的隔离；
- Popen 前后完整的持久启动意图、attempt CAS、所有崩溃窗口和 exactly-once 执行；
- 产物代际隔离、旧输出与当前 attempt 的完整归属验证。

停止确认只授予后续正常关闭流程的资格，不证明任务成功或研究结论有效。本变更的测试证据不能外推为真实 GPU/provider 验证、科研收益或已发布版本承诺；具体版本与测试结果由配套证据记录给出。
