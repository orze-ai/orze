# 新版工作后的兼容回滚与显式安装入口

已验证固定的升级协议版本可以接回新版执行后的当前 CPU 状态，保留新结果与累计支出。
同时为 `orze service upgrade` 增加显式 `--install`，使用既有项目专属安装器。
本片完成支持格式内的可执行回滚方案；真实 systemd、机器重启、生产上线和研究收益仍待验收。

## 真实版本和执行链

回滚目标 A 是已提交的 Core `f5885ba450b0a35fb2bfb000d587c3c80ead49ea`，完整保留
295 个包文件。每个文件都与该 Git 提交逐字节核对。候选 B 增加安装选项，其 CLI 和
升级模块字节与 A 不同；Pro、解释器、项目配置、数据库和 results 物理身份保持不变。
两版理解同一 `local_cpu_state_v1` 格式，没有数据库转换或旧授权改写。

两种源状态完成实际链路：A 执行并关闭 → 固定备份 → B 通过显式交接执行并关闭 →
为 B 的当前状态创建新备份 → 在 A 的实际导入环境准备反向交接 → A 再执行并关闭。
第二种情况在返回前还做了一次 B 的普通恢复。每种链路的三个原生 CPU 动作均完成，
A／B 的原始终态与预留记录保留；反向交接不改变源关闭记录。

原配置固定累计预留 180 秒，三个动作各预留 60 秒。返回 A 后再普通恢复，第四个动作
仍被 `wall_envelope_exhausted` 拒绝，没有建立第四条 attempt，也没有退还 B 的支出。
保留包的 runtime 身份与最终返回环境相符；已捕获控制器均以自有 pidfd 确认退出。

额外边界包括：A 的普通 recover 不能读取 B 的不同运行包；A 工作后的旧备份不能充当
B 当前状态的备份；两个反向请求完成源核验后同时竞争，仅一个取得授权和第三次动作。
备份不是旧数据库覆盖方案，返回不理解当前协议的任意历史二进制也不在支持范围。

## 安装入口与失败行为

`--install` 仅允许原配置为 systemd 的服务。准备成功后才调用已有 `install_units`，
沿用独立单元名、当前有效配置检查、主宿主就绪确认和 watchdog 启用顺序。
无此选项的准备操作保持不启动进程。

隔离的管理器替身覆盖成功、源准备拒绝、有效单元配置漂移、文件碰撞、计时器失败和
关闭结果未知。失败保留已发布的配置与单元；计时器失败只有在确认该宿主关闭后才取消
其自动启动，未知关闭不会继续 disable。无关项目单元和源配置字节始终保留。
这些是安装边界验证，没有调用真实 systemctl，也不证明真实 cgroup 或重启行为。

## 验证、独立复核与成本

基线保留 8 个缺少 `--install` 的失败和 1 个已有行为通过。首个产品候选 12 项通过；
当前 CephFS 上 3 条实际回滚链通过；Pro 相关回归 68 项及配对集成 51 项通过。
Core 全部服务／控制器交接相关回归 270 项通过。最终各运行的两仓源码与测试库存一致，
运行前后保持冻结。
本片没有重跑无关的全量；前一固定版本的两仓全量见[升级结果](2026-09-16-service-upgrade-results.zh-CN.md)。

标准库独立审计核对旧包原件、原始 SQLite、许可中的准确十进制纳秒、终态哈希、源
session 及交接代次。专项与 CephFS 集合各核对 3 个项目、9 个动作、12 次控制器出生、
9 条授权；同一脚本又核对 Core 相关回归中的三条链路，得到相同数量。
审计首版误将最终预算拒绝写入的 Stop 也要求不变而失败；第二版明确核验
唯一预期变化是 `stop_json: null → wall_envelope_exhausted`，其他旧字段仍逐个保持。
原脚本和失败日志保留，产品源码未因此变化。

包含 Python 启动的成功准备命令，专项 7 次中位数约 0.77 秒，CephFS 7 次约 0.84 秒；
这些混合正向／反向命令运行于小备份夹具，没有新旧提速对照，不能外推到大备份或研究速度。

证据包保留 6 次运行、6 份归档、18,307 个条目。公共 20 个载荷、私有
375 个载荷及归档成员逐项回读核对，最终源码与冻结候选一致。
