# 有界研究记忆：显式准备、发布与崩溃恢复

日期：2026-09-15。基线 Core `a5f1eb39aa16b162cd92a08e71ebbf9fcdcd222b` / Pro `a4bb5e1b2bdd85b7e9cc9b891fb40589ff6be34a`。本片新增 Core 存储接口与 62 项测试；Pro 产品源码不变。整体交接任务和 P2／P3 仍开放。

## 结果与接口

Core 新增 `read_stored_memory`、`prepare_memory_update`、`publish_memory_update`。调用方明确选择已有 SQLite 数据库、项目路径、操作 ID、预期前驱修订号和完整文档；发布还必须匹配文档 SHA-256。没有自动创建数据库、研究角色钩子、配置启用项或旧执行接管接口。原固定 JSON 文件读取与 Pro 来源解析仍使用原来的路径，尚未接入数据库记忆。

每个项目作用域最多保留一份当前文档和一份待发布文档，两者各受既有 schema 1 的 64 KiB／32 记录／64 引用限制。准备事务持久化待发布内容；发布事务同时替换当前内容并清除待发布内容。读者在同一只读事务内检查两者：存在待发布更新时明确不可用；成功读取也始终是 `pending_verification`，不会验证自然语言结论。

修订号按作用域递增，与文档格式版本、内容哈希和操作 ID 分开。A→B→A 的字节回退不会让旧前驱请求重新有效。相同操作 ID 必须连同前驱修订号及文档哈希匹配；提交完成但确认丢失后，精确重试可识别已提交状态。没有按年龄清理、覆盖竞争者或接管待发布更新的 fallback。恢复旧数据库备份、外部直接改表和命名空间移走再移回并不由这一协议解决。

记录保留规则允许追加新 ID，或为相同来源身份刷新绑定哈希；既有记录的文字、作者状态与来源类别不可改写，也不能删除或更换来源目标。发布阶段再次检查保留规则。需要修正结论时可追加新记录；容量满时整次更新失败。它保留记录结构，不证明语义压缩、重要性排序或科研结论正确，长期自动压缩仍未实现。

## SQLite 与故障语义

连接要求既有 `DELETE` 日志模式和 `NORMAL` 锁模式，不把 WAL 数据库改成另一种模式。仅记忆写入连接设置并核对 `synchronous=EXTRA`，既有全局 `FULL` 策略不变。SQLite 文档说明，在 DELETE 模式下 EXTRA 会额外同步删除日志的目录；此设置不能独立证明部署后的断电持久性。[SQLite PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)

两个准备者只能有一个待发布更新；无效文档在打开写连接前拒绝。提交开始后的错误返回 `unknown`，由精确重试核对持久状态；清理失败也使用结构化不可用／未知结果，原始 SQLite 错误不进入正式接口返回值。五个独立子进程崩溃点覆盖准备插入、准备提交、发布替换、删除待发布行及发布提交。

三个中途崩溃夹具通过测试专用的小缓存实际留下热回滚日志。只读读者拒绝恢复写入，原文件字节不变；显式写入重试完成回滚恢复后继续同一操作。进程退出、注入异常与本地 `/tmp` 成功不等于 CephFS／网络文件系统或真实断电验收；SQLite 原子提交依赖底层锁与同步语义。[SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)、[SQLite over a Network](https://www.sqlite.org/useovernet.html)

## 保留的基线与原型缺陷

- 原有格式、SQLite 策略、来源与报告分页基线：112 通过，17.00 秒。
- 新测试在旧版本失败：缺少 `orze.research.memory_store`，1 失败，0.31 秒；日志原样保留。
- 首个存储原型：75 检查／59 子进程。它允许完整替换删除旧反证，此反例保留。
- 加入保留规则：86 检查／70 子进程。删除反证、改写字段和更换来源被拒绝；ABA 验证使用绑定变化，避免把文字改写当作允许操作。
- 故障、策略与容量原型：73 检查，保留回滚清理异常越过结构化返回的缺口；正式候选新增对应处理与测试。
- 正式候选定向：174 通过，27.97 秒；源文件与测试未在运行期间变化。

这些数量包含明确标为已观察缺陷的原型检查，不把它们全部视为产品正确性验收。最早未运行、未完成的 `store-v1.py` 草稿也随原型归档。

## 实际 CPU 产物与重启

两个隔离 CPU 项目生成相同的合成报告；作者分别写下 confirmed／refuted 解释。四次 CLI 调用、38 次记忆子进程调用（14 读／14 准备／10 发布）及八次来源捕获完成。准备后或发布后、返回给调用方前退出的两次 73 状态保留为空 stdout，并由新进程读取和精确重试确认。

每个项目经历三次修订：首次存储、来源绑定刷新、追加未确认记录。原作者结论保留；来源污染后捕获明确不可用，恢复旧字节产生不同绑定。普通记忆读者仍返回待核实作者文档，不能据此把失效来源当作当前证据。来源捕获在记忆写入前后相同，说明无关记忆表写入没有让持久来源绑定自行失效；活跃 pager 的数据库版本仍需要重新检查。

核验检查实际 `action` 尝试、`TREE_CLOSED`／`ECHILD_WALL`、已结算预留、产物生产者与内容哈希。`ideas`、`execution_attempts`、`cpu_action_reservations`、`research_artifacts` 四表在发布、读取及 CLI 重放期间保持不变。Core 子进程禁用 Pro 导入；许可替身仅在隔离 Pro 捕获／核验进程内使用。没有 provider、真实模型、GPU 或真实多轮研究验收。

## 新接口成本

四组本地夹具，每次调用重新打开／关闭 SQLite 连接；两轮计时按相反案例顺序，每组 12 个准备→发布→读取循环。数据与期望结果预先在内存中，初始化不计时；每次输出、原生表不变和最终一当前／零待发布行均核对。单独两轮 tracemalloc 不与计时或全量回归重叠。

容量案例使用 32 条 unknown、零引用记录及合法尾部空白补足 64 KiB，不是最复杂语义文档的最坏情况。其两轮 Python 峰值：准备 335,005／335,477 B，发布 335,485／336,126 B，读取 238,441／239,817 B。读取返回时 current 34,924／36,970 B，释放结果并 GC 后 650／2,696 B；原始逐样本 current／peak／after-GC 与进程 I/O 计数均保留。

这是新增能力的成本，没有旧等价功能提速对照。tracemalloc 不包含 SQLite 原生分配，不是 RSS；每作用域的记录上限不是整个数据库、回滚日志、文件系统或每轮研究 I/O 的硬界限。空闲页仍可保留在数据库中。
