# 按状态合并索引结果：减少源排序和密集候选成本

本片基于 Core `f9d69e24c3a31569cb8235d617366b5d5a8894f5`、Pro `78ba34a54ca05a3dc4081b52cc7859d70013b0fa`。旧配置身份准备和正常准入的两组候选查询，分别使用四个状态的有序索引结果合并。默认索引、本机 SQLite 3.37.2 下，新查询计划不再使用对应的临时 B 树排序。完整身份修补没有稳定耗时收益；密集候选的拒绝路径有可重复的局部收益。

## 实现与资格边界

四个 `status COLLATE NOCASE = ?` 分支覆盖原先的 queued／pending／running／completed，互不重叠。单条 `UNION ALL ... ORDER BY rowid` 查询保持全局顺序；缺失身份复制仍是一条 SELECT 的读快照，全部派生完成后才在主库一次比较当前文本并写回。

准入仍分匹配 hash 和缺失身份两组，并共用 1,025 条返回额度。每组的 LIMIT 放在四状态合并之后；总量超过 1,024 时仍在资格解析前拒绝。没有把每个状态分别截断后当成完整历史。当前 kind 筛选、配置读取检查、当前 YAML、首个有效所有者及前置不可用记录的规则保持原样。普通入口和调用者自有事务入口的写入、提交／回滚代码未改。

未强制索引名称；删除可选索引的语义检查继续通过，代价可能增加。查询计划和 opcode 结果属于本地 SQLite 观测，不是跨版本或任意存储的硬保证。完整历史派生、单条配置／YAML 展开、暂存磁盘、逐条事务和其他历史读取仍有成本。

## 基线、差分与实际执行

- 135 项既有检查在原件上通过。
- 新源首批读取、匹配组首行、缺失组首行成本检查在原件上分别失败于约 40,600、50,400、54,700 条 SQLite 指令；同轮 18 项顺序／资格检查通过。原始失败保留。
- 最终定向 156 项通过，29.06 秒。覆盖大小写状态、rowid 空洞／顺序、hash 与 source 缺失组合、可选索引缺失、跨状态／候选组的不可用优先级和首个所有者；已有并发和事务失败检查继续通过。
- 一个既有测试只扩大 source cursor 观察器的查询识别条件，以覆盖新增排序列；读取上限、批次、关闭、写入和哈希断言全部保留。旧测试原件另存，机械核验逐 AST 比较这一处变化。
- 64 组混合元数据，普通／调用方事务入口共 128 对新旧结果、256 次实际准入调用，完整数据库结果一致。每种入口各 31 次 duplicate、28 次 unavailable 拒绝、5 次插入；调用方事务均能回滚。固定时钟仅用于对照元数据投影。
- 新项目再经真实 ingress 准备 1,500 条缺失身份，接受一个 CPU action、保留其重复提案。真实 worker 生成 `10`，完成 `TREE_CLOSED/ECHILD_WALL`、SETTLED 和 SHA 核对；三次 Core CLI 启动包含空初始化、执行及新进程回放。回放不新增执行、扣记或产物。历史行是导入元数据，不是已执行的研究。

## 完整身份准备：时间基本持平，写入与 SQLite 分配下降

两轮各用独立数据库，旧／新交替三次；输入复制、打开数据库和最终逻辑摘要核对在普通计时之外。两轮所有旧／新修补结果完全相同。

| 行数／payload 字符数 | 第一轮旧→新，秒 | 第二轮旧→新，秒 |
| --- | ---: | ---: |
| 100／1,024 | 0.11947→0.11945 | 0.11816→0.11910 |
| 1,000／1,024 | 0.89287→0.87775 | 0.86593→0.87509 |
| 5,000／1,024 | 4.24451→4.25810 | 4.19865→4.19140 |
| 500／8,192 | 2.54454→2.53268 | 2.52982→2.52234 |

5,000 条约 1 KiB 配置的进程写入计数约 34.12→28.79 MB，500 条大配置约 21.86→17.74 MB；100／1,000 条没有写入量下降。暂存数据库大小不变，下降的是查询相关额外开销。`/proc/self/io` 不是生产共享存储流量或 fsync 次数。

独立 SQLite allocator 运行，5,000 条的峰值约 5.06→2.93 MB，500 条大配置约 5.13→2.97 MB；1,000 条约 4.48→2.48 MB。计数定义见 [sqlite3_status64](https://www.sqlite.org/c3ref/status.html) 和 [SQLITE_STATUS_MEMORY_USED](https://www.sqlite.org/c3ref/c_status_malloc_count.html)：它不含另行配置的辅助 page cache，不是完整 RSS。

另一次 Python `tracemalloc`，5,000 条峰值为 468,739→454,204 字节，500 条大配置为 2,296,660→2,282,125 字节。行集合在前片已经分批，不能把本片 SQLite 分配下降解释为同样幅度的 Python 或总内存下降。100 条最先执行的分配样本也保留，不用冷路径推断线性增长。

独立 writer 观察每次仍为一次 BEGIN／COMMIT。5,000 条两轮主库区间为 97.95→99.03 ms、97.97→98.75 ms；500 条大配置为 43.50→43.46 ms、42.41→42.56 ms，没有锁时改善证据。暂存仍用 DELETE／FULL／normal、512 KiB page cache 和 0700 私有目录。

## 128 次准入：密集候选收益与负对照

每轮先预热，再旧／新交替三次。下表前七行走完整 ingress，包含相同的返回／作者源核对开销；后三行明确是同一预先准备提案的 128 次直接准入，没有 ingress 旧身份修补，不能横跨这两种入口比较绝对耗时。四种状态按固定顺序混合，旧／新源和数据库均不变。

每次均保留 128 个 writer／回滚，资格解析次数一致：完整 ingress 相同文本为 256、语义匹配为 384；这里的直接准入控制为 0。容量拒绝仍先于历史 YAML 解析。正常计时不包含单独的 SQL／解析计数、Python tracing 或 SQLite allocator 观察。

不能从这些点把旧成本外推为随全部历史线性增长。旧版已受 LIMIT 和 SQLite 优化影响，5,000→20,000 时直接缺失候选的指令计数也没有继续增长。新版本减少了这组实际读取／排序代价；小／稀疏或仅语义匹配场景没有同等或稳定收益。

完整密集 ingress 的峰值仍随规模增长：20,000 条两轮 Python peak 约 5.98 MB，旧／新基本相同；SQLite allocator peak 都约 4.64 MB。5,000 条密集 ingress 的 SQLite peak 都约 3.63 MB。1,000 条有效密集候选的 Python 分配还略增约 1–2 KiB。独立的缺失身份直接准入观察，5,000 条 SQLite peak 约 2.05→1.84 MB。这些区别及全部逐次样本均保留，不能把源查询的局部内存收益套到完整 ingress。
