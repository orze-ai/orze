# 记忆更新：在调用与写入前拒绝缺失的 Core 能力

## 问题与改变

显式 v2 记忆更新原来按使用顺序导入 Core API。搭配具备读取／准备／发布、却缺少 pending 检查接口的旧模块时，消费者可以先调用 provider、写入待发布文档，随后才返回更新不可用。普通记忆读取也随之被 pending 状态阻塞。

修正版在 v2 初始化时检查四个所需接口是否可调用，缺失或不可调用即返回 `research_memory_unavailable`。检查不试写数据库，不调用 provider；v1 只读消费继续使用自己的既有要求。正常的准备、发布、预算、来源复核和精确恢复流程保持原样。能力存在仅是最低准入条件，不证明任意旧 Core 版本的协议语义兼容，也不覆盖进程中途替换模块的任意行为。

固定基线 Core `c498da1147c98b3a94fb95bdbfcc8126157430c1`、Pro `e5ba053a37137b7cdfb7fd341e879cd88213d45c`。Core 产品源码未改变；Pro 仅在初始化加入五行检查，新增 18 项边界用例。机械核验去掉对应三条 AST 语句后，整个模块与基线一致；其余原有源码／测试按 Git blob 核对。

## 保留的旧版失败

既有 429 项回归先在旧源码通过。新 18 项用例在旧源码得到 8 通过、10 失败；修正版合并定向测试 447 项全部通过。

16 个缺失／不可调用场景分别覆盖四个 API、当前记忆和预先准备的更新。旧版记录中有 8 次 provider 调用、6 个数据库发生改变、2 次 `ImportError` 泄漏；这些计数互有重叠，不能相加。另有两个失败仅涉及拒绝时点／错误码：它们原本已是零 provider、数据库不变，不算成写入缺口。修正版 16 个场景均为零 provider、原数据库与提案字节不变、没有异常泄漏。另两项用例证明 v1 不依赖三个更新入口。

独立实际产品反例加载了 Core `efd4bba2426c8d074527d5acfb5387af849f9ffd` 的完整原始 `memory_store.py`。与当前文件的 AST 差别仅为缺少 pending 检查函数；其余 Core 模块保持当前版本。这是固定模块组合验证，不能称为完整旧版安装验收。

该反例先运行一个真实 CPU 源报告，再显式建立一条作者记忆。旧消费者实际调用一次离线 provider，并准备第 2 修订；随后返回 `research_memory_update_unavailable`，普通读取变为 `memory_update_pending`。前后数据库原字节、原记忆、追加文档、operation／revision／SHA、实际提示词与响应均保留。执行、结算、产物和提案表前后相同，新增 pending 单独核实；失败根没有被修复或覆盖。

准备基线文档时还发生一次工作区清洁断言失败：准备器先创建私有证据，随后把自身新增文件视为脏状态。已有六份 Core 快照保留，按 Git 原件逐字核对后继续创建剩余材料。该准备失误不计作产品失败。

## 修正版实际链路

两个隔离项目分别保留 confirmed／refuted 作者声明，共四个真实 CPU worker、六次 Core CLI、二十个新研究消费者、二十次离线传输调用。另有四个初始记忆管理子进程和两个来源捕获子进程，分别计数。旧版失败项目的一个 CPU worker 另列，不混入修正版四个。

每个项目中，真实旧模块的 v2 当前记忆和显式 pending 恢复都在 provider／写入前拒绝。当前记忆拒绝与 v1 只读分别比较数据库、提案、配置与来源文件的前后原件；pending 拒绝则比较数据库原件和精确 intent。相同旧模块的 v1 只读能够消费完整记忆，仍不写入这些输入。

当前模块则完成显式追加、实际后续 CPU 提案、prepare／publish 后进程崩溃、精确恢复、来源刷新和新进程重读。两个 CPU 后续产物记录实际收到的记忆修订、原声明、反例和未知事项；声明仍为未验证。完整提示词清单、请求预算与 provider 扣记、`TREE_CLOSED`／`ECHILD_WALL`、SETTLED、产物 producer／内容 SHA 及无重复记账的 CLI 重放均已核对。

许可替身只用于隔离 Pro 进程；外部模型、账户、GPU 和现有服务调用均为零。本片验证能力缺失时的副作用边界及兼容行为，不是科研质量、生产兼容或整体提速验收。正常路径只增加入口能力检查，未进行耗时／内存收益对照，也不宣称没有额外开销。
