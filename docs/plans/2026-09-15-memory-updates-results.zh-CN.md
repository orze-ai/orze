# 显式记忆更新、原请求恢复与数据库身份复核

## 本片结果

实际研究消费者现在支持显式 `research_memory: {version: 2}`。模型可以用独立 JSON 响应追加派生笔记，或刷新已有记录的原来源绑定；下次请求会读取新修订，并继续使用本次请求和 provider／角色预算。版本 1 保持只读，缺失／null 保持原行为。

基线为 Core `1c1f5bcf7391afc7416e74f316d9aca80ae5d84c`、Pro `85a56ab20366364d9dc4b3b90557659c12267c8c`。Core 新增 `inspect_pending_memory` 和 23 项测试；Pro 接通更新、恢复及读取器重建，新增 59 项测试。已有 Core API 在移除新增函数后 AST 完全一致；Pro 原有路径在撤回明确新增的接入逻辑／初始化重构后 AST 一致，其他已有源码、测试与示例逐个核对 Git blob。

Core 检查接口只读，不建表、不修复、不发布。它返回 prepared 文档的原始 JSON 文本、摘要、操作 ID、前驱和修订，验证当前／待发布关系及旧记录保留规则。原始空白也参与摘要；恢复不能重编码文档后冒充原请求。

v2 的 `max_updates` 为 1–4，默认 1；`resume_prepared` 必须是布尔值，默认 false。显式开启恢复意味着可以完成此逻辑项目已有的 durable prepared 意图，包括操作员准备的文档。缺失记忆不会自动创建；初次使用需要显式准备／发布。恢复仍受当前规则、配置、停止状态和决策准入约束，不恢复旧执行所有权。

更新响应仅允许 `{"update_memory":{"entries":[...],"refresh":[...]}}`。整个 v2 响应为严格 JSON，最多 65,536 UTF-8 字节；重复键、非有限数、混合控制／提案和嵌套更新控制均拒绝。模型只能给出新记录内容和来源 idea ID；主机生成操作 ID、前驱和绑定摘要，新增记录标为 derived。旧文本、作者状态和来源身份不能改写／删除；记忆格式容量或来源不足拒绝整次更新，不静默丢弃反例。64 KiB 存储上限并不保证新记忆能放入任意项目的提示词预算；发布后下一提示词若超限会明确阻塞，前瞻提示词容量准入仍待处理。

更新消耗当前模型请求。最后一次请求可以发布记忆，但以 `research_memory_updated_request_limit` 返回 blocked，不能声称生成了提案或研究收敛。每次写入后重建证据视图、重新选择可见 ID，并重读上下文、已有 ID 和谱系；每通道最多 32 个可见 ID 跨过写入，更大的视图须先显式缩小。扫描标识和游标更新，之前的遍历覆盖不延续。原 provider 和角色预算观察器继续使用，扣费记录和请求序号不重置。

数据库文件及全部父目录的 device／inode／mode 在整次 v2 调用中固定，每个输入检查点重新比较；新读取器还必须匹配原数据库／结果目录身份。正常 SQLite 写入改变内容，不能因此接受同内容的文件或目录替换。未知写入回执只有在读回完全一致的修订、操作 ID 和摘要后才确认；否则保留未知或待处理状态。

这些检查是可观察边界复核，不是 provider、数据库和所有来源文件之间的原子事务，也不证明任意命名空间 ABA、备份回滚或生产文件系统的持久性。所有自然语言声明仍为 `claim_verified: false`；来源 current 不等于声明为真。

## 保留的失败与回归

固定基线 333 项通过。旧 Core 缺少 pending 检查 API、旧 Pro 拒绝 v2 的两个单项失败均保留。首候选 110 项通过；扩展负例后发现两个真实缺口：更新控制混入提案列表时仍追加了一条提案，停止的 pending 项目仍进入决策整理。后者的测试替身只记录调用并返回 HOLD，不表示真实决策状态被写入。修正严格控制识别和停止检查后，425 项通过。

随后复查发现跨自身写入的数据库身份缺口：四个探针分别在 prepare／publish 后替换数据库或其父目录，候选仍进入第二次 provider 请求；prepare 场景还发布了替换后的待提交文档。四项失败、原数据库／目录现场和原始日志完整保留；它们没有追加提案，不能描述为实际执行接管。加入整次调用的路径身份复核后，最终定向 429 项通过。

早期包装式 pytest 调用未指定 JUnit，保留并核对其原始 stdout 计数，没有补造 XML。命名空间探针、最终定向和全量回归均有原始 JUnit。最终结果：

- Core：5171 passed, 7 skipped, 2 warnings in 1127.81s (0:18:47)。
- Pro：1465 passed in 426.81s (0:07:06)。
- 配对：31 passed in 0.88s。首次运行因未启用隔离许可替身而为 25 通过、6 跳过；原结果保留，补跑才计入完整配对覆盖。

测试集合重叠，不能相加。每次运行使用唯一短 basetemp；源码／测试前后指纹一致，所有验证进程关闭后才修改源码。

## 实际 CPU、传输与重启链

修正版的两个隔离项目分别从 confirmed／refuted 作者声明开始。四个实际 CPU worker、六次 Core CLI（含重放）、四次 Core 初始记忆进程、两次来源捕获、14 个实际研究消费子进程和 18 次离线传输替身调用通过。另一个前候选同规模链路也保留，不能把两轮合并描述成更多研究场景。

第一次模型响应追加派生反例和未知笔记，第二次使用修订 2 提出 CPU 后续动作。产物逐字记录原声明、派生反例、未知状态和三个 false 验证标记。核验检查 attempt、`TREE_CLOSED`／`ECHILD_WALL`、SETTLED 预留、producer／产物哈希、原记录保留和重放不重复执行。

后续进程分别在准备、发布完成后退出 73；新进程以同一身份恢复修订 3／4，来源刷新产生修订 5，最终冷读仍保留五条记录。测试还让两个新恢复进程竞争同一意图，确认没有额外修订。实际离线 OpenAI 传输路径的输入／输出预留跨记忆提交保留，下一提示词中的扣费链和剩余预算一致。

外部模型和 GPU 调用为零；真实 CPU 产物证明链路连通，不证明作者／派生声明为真，也不构成真实多轮科研质量或 P3 验收。

## 核验与剩余工作

18 份归档含 24,668 个普通文件和 354 个链接条目、2 个 FIFO 类型条目，保留硬链接身份元数据。首次归档未处理 FIFO 而失败，原日志和五个已产生的归档文件均保留，新版归档只读取普通文件内容。首版预核验还因按字典 repr 排序行而误报不一致；新版本按键规范化比较，原始值与重复行数量完整保留，失败脚本与日志也保留。原件、失败现场、提示词／响应／清单、SQLite 文件、CPU 产物、所有成本样本和脚本均机械核验；核验由同一代理启动的独立 Python 进程完成，不等于独立人工审查。

预核验 SHA-256：`8831c8f424da3c11ca399b5a3373d4d258e9ea1f46c228ac4b239c70194a4eeb`；最终 verification.json SHA-256：`5af5d6b90ff50d76d781bc45bf8f217ab8496300d6cdd0b2abd71a8872199af0`。v2 本片验收使用新增 pending API 的配对 Core；旧 Core 的 v2 提前能力检查仍待补齐，不把它描述为已支持。Core 发布自身代码、测试和回归；Pro 源码、配对清单与完整私有证据由[私有证据索引](../evidence/2026-09-15-memory-updates-pro-private-index.json)固定。

语义压缩、容量不足时的研究策略、关键反例选择和真实多轮研究质量仍开放。P1 的全历史成本、CephFS 角色释放／GC、状态兼容、隔离／备份／回滚、真实许可／模型资源与受控上线，以及跨领域等质量 P3 验收仍需继续；整个产品目标未完成。
