# 角色与 provider 预算进入联合研究快照

显式 `research_evidence.version: 2` 现在将报告、提案、CPU 观察、请求次数、角色 attempts／token／费用预留与 provider token 预留放入同一个必需 JSON。联合上限仍为 4–32 KiB；没有扩大 prompt 上限。当前消费链的预算联合项完成，整个产品目标继续按[交接 TODO](2026-09-14-machine-handoff.zh-CN.md)推进。

## 行为与边界

- 角色预算使用现有持久账本的完整只读校验。有有效 baseline 才显示总量；旧完成次数计入 attempts。缺失 baseline 或当前角色身份明确不可用，不编造零开销。
- native 角色视图要求当前 attempt、角色策略、预留金额和进程 token envelope 一致。账本匹配不授予新启动权，也不代表进程所有权已经核实。
- provider 视图观察实际 transport 前的 token 预留。每次重试或 fallback 都可能再次扣记，包括失败调用；观察不初始化、重置或退款。未确认的 provider 状态变化会拒绝该进程后续调用，新建视图不能绕过。
- provider 扣记发生在角色已经预留的 token envelope 内，不能把两者相加当作两笔费用。两者都不是实际 token 使用量或账单；provider 剩余值仍须覆盖下一次输入、framing 与输出。
- 每个新视图完整审计角色账本一次；发布、provider 前后和追加前核实共同来源、配置、路径／PID／nonce 与账本状态。writer lock、损坏、替换、删除或不确认的变化会拒绝混合视图。
- 已核实的 `null` 上限表示声明不设限；未初始化、未配置和不适用分别表达。大记录保留 ID 和不可用原因，必需元数据无法装入上限时在 provider 前拒绝。

账本沿用 8 MiB、32,768 条和单条 16 KiB 的读取边界，但完整审计仍为 O(N)。32 KiB JSON 上限不是全流程 I/O、历史校验或 Python 内存峰值上限。

## 实际运行与重启

主验证在两组各 260 条历史上，经真实角色预算准入、命令构造、READY–GO、research CLI 和角色关闭运行。实际 Gemini adapter 使用离线 transport；每组 11 个研究请求、12 次 transport 尝试，首个失败触发 fallback，失败预留保留。

角色账本显示全局 4 attempts、2,000,000 token、100,000 microUSD。其中两次旧完成次数是导入夹具，critic 费用是通过真实预留 API 建立的先前未启动预留，没有 critic 工作进程。两组最终 provider 预留为 706,596／706,479，均在本次角色 envelope 内。

两组分别使用末条合格来源，或排除污染的末条后使用前一条；定向读取恢复被容量省略的大提案。22 份 native prompt 清单、实际预留链、两份全局基线 decision contract、两次 CPU action、产物与 SETTLED 终态均可关联。角色和 CPU 工作进程都有 `TREE_CLOSED/ECHILD_WALL` 关闭证明。

**配置边界：**Core CPU queue 仍拒绝同时启用 provider／legacy roles。首版混用配置被拒绝并保留失败。成功运行预先写定两个合法配置，顺序完成 research 角色和 CPU 执行；角色快照的 CPU 块明确为 `not_applicable`。这没有证明两种 profile 可以并行混用。

兼容控制使用上一片未修改的 CPU 产品脚本，再完成两次 CPU action／22 个假 provider 请求；其中 CPU 观察有效，角色 baseline 未初始化，provider envelope 未配置。四个 CPU 项目均在新进程中回放，未新增执行、预留或产物。

另一个真实角色项目把启动次数上限设为 1：当前角色取得最后一次预留后仍完成空响应，结果为 empty／软失败。新进程没有内存计数，仍由持久账本拒绝第二次启动；没有第二个 worker 或 provider 扣记。

这些是实际进程、准入和 CPU 执行验证，模型 transport、许可检查及历史有隔离替身，不构成真实模型、生产许可或科研收益验收。

## 额外成本

两轮各在新项目中测量 0／256／4,096／16,384 条合成预留记录。旧 v2 只含 CPU／请求预算，新版增加角色／provider 预算；两者都完整提供同样的 16 个报告与 16 个提案。每种版本五次交替计时，包含首次读取、打包、五次发布前复核与关闭，内存峰值另跑。信息不同，不能作为等信息量提速对照。

| 0 | 175.79／173.98 | 179.35／177.07 | 1.19 |

最大账本约 1.93 MB，新联合 JSON 为 12,514 字节，旧版 11,108 字节；后续五次复核约 81 ms，没有再次完整重读角色账本。新增历史校验的时间和内存成本均保留，不声称科研提速。尾部重复记录的负对照验证完整拒绝，没有因载荷有界而跳过尾部校验。

## 回归与证据

最终 Core 一次全量 4,905 通过、7 可选 Pro 跳过、2 既有 warning，966.94 秒；Pro 全量 1,152 通过，304.73 秒；配对 31、最终定向 92 项通过，输入冻结。集合有重叠，不能相加。本片 Core 产品源码／测试未变，Pro 原有测试未修改。

保留了三个失败：首次定向测试发现 provider 非法状态拒绝未锁存（1 失败／46 通过），随后修复并扩展到进程级锁存；首次产品脚本使用不合法的 CPU／role 混合配置；首次成本脚本捕获了错误的异常类型，实际尾部重复记录已经被产品拒绝。中间源文件、原始输出及新目录复跑均保留，未改写失败记录。

最终独立进程机械核验检查冻结输入、Git 原件、3,382 个归档文件、native prompt／扣记链、角色与 CPU 终态、重放及成本数据。核验脚本首轮错误假设角色配置必有 `enabled` 字段；按现有缺省启用规则修正，新目录复跑通过，失败脚本和日志保留。这是机械核验，不是另一位审阅者。完整 Pro 库存、prompt、日志和归档留在私有仓库；[private index](../evidence/2026-09-15-research-budget-snapshot-pro-private-index.json)固定实际配对提交和 Git 对象。Core 原始全量记录位于[本片运行目录](../evidence/runs/2026-09-15-research-budget-snapshot/)。

其他 Pro consumer、全历史 qualification／家族映射、sidecar 重复扫描、持久记忆、真实模型长程研究、CephFS／生产部署与端到端等质量收益继续保持未完成。
