# 联合研究快照：容量、额外读取成本与实际 CPU 验证

本片将报告证据、Idea Lake 提案定义、CPU 账本观察和本次请求次数接入 Pro 的同一个必需 JSON 快照。协议显式启用，旧 v1 行为保留。角色 attempts／token／cost 账本和 provider 的进程内 token 预留尚未纳入此 JSON，因此完整预算联合快照仍有后续工作。

## 使用与边界

```yaml
research_evidence:
  version: 2
  page_size: 16
  proposal_page_size: 16
  max_requests: 32
  max_snapshot_bytes: 32768
```

- 联合 JSON 上限默认 32 KiB，可设 4–32 KiB；两类页长各 1–32，一次调用最多 1–256 个请求。整个 prompt 的既有上限仍独立生效。
- Objective、来源／作用域、页信息、账本与请求额度完整保留。可见 ID 不消失；大记录或容量放不下的内容带不可用原因，不能截成看似合格的结果。必需元数据本身过大时，在 provider 前拒绝。
- 两类读请求共用额度；一次替换一个频道，另一频道保持当前视图并重新核实。定向选择较少 ID 可恢复容量省略；超出单记录界限的内容仍不可用。
- 提案定义只是 Idea Lake 的历史元数据，未消费的源文件不在此频道覆盖范围。它不等于合格证据、有效执行配置或指令。指标结论仍由当前原件资格支撑。
- CPU 预算观察完全只读。未初始化返回未知，不创造免费额度；已核实 v2 的 `null` 表示声明不设累计预留 envelope 上限，不表示实测 CPU 用量或执行许可。请求次数也不等于剩余 token 或费用；原有角色预算和 provider token 准入仍各自执行。
- 每个新视图完整审计预算一次；发布、provider 前后与追加前重新检查共同数据库／配置版本、可见原件、提案及本地 HOLD。来源、schema、账本、Stop/HOLD、配置或数据库身份变化时拒绝混合视图。没有跨调用缓存。

“读完所有页”保证的只是 ID 枚举范围。容量省略可能需要额外读取，枚举结束、额度耗尽或不可用记录都不表示科学收敛。若另一个频道一直保留大记录，后续页面会反复付出恢复成本。

## 实际产品链

两个项目各导入 260 条历史，前四个提案各约 6 KiB；一组最后一条来源有效，另一组带污染标记。真实空 Core CLI 初始化账本，真实 Pro CLI 通过确定性离线 provider 读取联合快照并提交带全局基线 decision contract 的 CPU action。

- 每组 11 次请求：恢复被容量省略的提案、选择后页定义，再继续读取报告后页；首视图四个提案 ID 全保留，其中两个不可用。
- 两组分别采用第 259 条合格来源，或排除污染的第 259 条而采用第 258 条。产物包含实际所选定义 SHA。
- 22 份原生 prompt 清单、两份 admission receipt、两次 CPU 执行、产物、进程树关闭证明和预算终态可关联核验。24 KiB 配置下实际最大快照分别为 24,445／24,443 字节。
- 两次独立重启没有新增执行、预算扣记或产物。有限 20 秒累计预算与声明无累计上限分别覆盖。

这里有实际 worker 执行与结算；provider 是离线替身，历史是导入夹具，不是实际模型、生产许可或科研收益验收。

## 容量成本，包含负结果

两轮独立项目分别测 16／256／1,024 条历史，首视图每种版本五次交替计时；Python traced peak 与完整读取另跑。v1 只读报告，v2 多读提案和账本，不能当作等信息量提速对照。完整读取包含必要的定向恢复请求，并要求找回全部合格报告与完整提案定义。

两轮结果如下，每格按第一／第二轮列出。完整 v2 覆盖两类内容，完整 v1 仅覆盖报告；表格呈现额外开销，没有等质量提速结论。

| 历史条数 | v1 首视图 ms | v2 首视图 ms | v1 完整读取 s | v2 完整读取 s | v2 视图数／其中恢复 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 16 | 45.04／45.93 | 117.10／118.30 | 0.045／0.045 | 0.171／0.172 | 3／2 |
| 256 | 45.25／45.33 | 117.35／118.64 | 0.505／0.508 | 3.576／3.593 | 66／35 |
| 1,024 | 44.92／45.38 | 116.74／117.81 | 1.970／1.989 | 14.312／14.433 | 246／119 |

首视图 Python traced peak 约为 v1 的 1.12 MB、v2 的 1.21–1.22 MB。在 256／1,024 条历史中，v2 首视图保留两类各 16 个 ID，但只有 9 个完整合格报告和 8 个完整提案定义，其余带不可用原因；后续请求才恢复内容。完整视图数包含重复验证，预算审计数与每个新 v2 视图一一对应。

测量与隔离的本地回归运行有时间重叠，绝对耗时可能受主机负载影响。两轮仍暴露相同的额外成本，尤其是持续持有大提案页面时的反复恢复；不能用单块有界替代对完整研究成本的测量。

## 验证记录

Core 一次全量 4,905 通过、7 可选 Pro 跳过、2 既有 warning，972.97 秒；Pro 全量 1,111 通过。Core 定向 31、Pro 定向 77、配对 31 项通过，集合有重叠，不能相加。全部运行输入保持冻结。

保留三类验证脚本失败：启动命令括号错误而未运行测试；空控制循环尚无 attempts 表；成本脚本把遍历结束误当作完整内容覆盖。分别修正启动命令、无执行检查与计入额外恢复请求，使用新目录重跑，原件保留。首轮实现／测试也保留，后续只给 proposal kind 增加 SQL 返回前尺寸检查并增加边界用例。

最终独立进程机械核验通过：原有 280 个 Core 源文件、515 个 Core 测试文件、89 个未修改 Pro 源文件、142 个 Pro 旧测试文件按 Git 原件核对；Pro 两个既有修改文件中无关函数／类 AST 保持一致。6,887 个归档文件、冻结输入、失败与成功运行、22 份实际 prompt、receipt／attempt／settlement 与重放逐一核验。这里没有另一位独立人工或 agent 审阅者。

完整 Pro 源码库存、原始 prompt、日志和项目归档留在私有仓库；[private index](../evidence/2026-09-15-joint-snapshot-pro-private-index.json) 固定配对 Pro 提交及证据 Git 对象哈希。Core 原件在 [本片运行记录](../evidence/runs/2026-09-15-joint-snapshot/)。
