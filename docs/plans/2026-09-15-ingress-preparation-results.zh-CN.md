# ingress 仅准备旧身份：去除未使用的历史映射

本片基于 Core `1b8ac7b5e7a398ceae95f58bbd47e8b3ae0ab895`、Pro `8ca58e9351f209209db9a9a4c3b7ceb9d276d433`。真实 ingress 保留必要的旧身份修补，跳过随后返回值被丢弃的 owner 映射查询。密集历史的完整 ingress 峰值下降；小／稀疏历史没有稳定耗时收益。

## 改动与保留规则

IdeaLake 新增 `prepare_admitted_config_hashes`，与现有查找方法使用同样的完整输入规范化，然后在有合法 hash 时调用原修补逻辑。空输入、无合法 hash 和已知同 ID 批次不访问旧身份历史。生成器晚期失败仍发生在任何 SQL 之前。任何非空合法请求仍可能准备所有缺失身份，单条配置／YAML、源快照暂存、完整派生和主库事务的成本没有消失。

ingress 优先使用准备方法；轻量适配器没有这个可调用能力时，继续调用现有 `find_admitted_config_hashes`。公共查找 API 及其他 IdeaLake 代码完全保持原样，既有其他消费者仍得到首个 owner 映射。准备出错仍进入普通准入，由当前写事务的实际状态、kind、配置和共享候选容量决定结果；准备 API 的返回值没有去重或 ACK 权限。

源锁、pending hash 计算、当前读入、正常插入和 ACK 代码保持原样。两个既有测试把真实源锁移除／并发配置改写的注入位置迁到实际准备边界；每个业务断言保留，旧测试原件及逐 AST 机械比较可复核。

## 基线、真实路径与失败记录

- 基线既有 156 项通过，29.03 秒。新增两个成本检查在原件上失败：真实结果正确，但都观察到被丢弃的 owner 查询。
- 首轮定向 170 通过、1 失败：新负对照夹具遗漏正常提案所要求的 `queued`，先被 `proposal_requires_queued` 拒绝。仅补正夹具状态；失败日志和原测试保留。最终定向 171 项通过，32.28 秒。
- 15 项新增检查覆盖稀疏／密集查找、1,500 条旧身份准备后合法入队、完整输入消费、无 SQL 空请求、公共 first-owner／源变更、两种旧适配器回退、准备故障后的实际插入／重复／容量拒绝和同 ID 重放。
- 64 组实际完整 ingress 对照，各用独立 SQLite 和主文件／sidecar；包含缺失与错误缓存、损坏／非文本／过大配置、状态／kind、可选索引缺失。共 256 次正常准入调用，每侧 29 次插入、28 次重复、71 次不可用拒绝；完整数据库、原始提案及作者源结果一致。固定 transition 时间只使投影可比较，不代替 worker。
- 另一个新项目导入 1,500 条历史元数据，直接准入先因缺失候选过多拒绝，真实 ingress 准备后接受一个 CPU 动作、保留其重复提案。真实 worker 产出 `10`，有 `TREE_CLOSED/ECHILD_WALL`、SETTLED 和产物 SHA；三次新 Core CLI 包含初始化、执行、回放。回放无新动作、重复扣记或产物。导入历史不是已执行研究。

## 两轮完整 ingress 对照

每个样本处理 128 条保留的跨 ID 提案；已有身份均绑定当前文本。两轮各先预热，再旧／新交替三次。直接加载保存的旧 ingress 与当前 ingress，使用同一未改公共 lookup／正常 admission；没有替换实例返回结果。设置、数据库完整投影和独立计数在普通计时外，函数内相同的作者源／结果核对成本保留。

| 历史／情形 | 第一轮旧→新，中位 ms | 第二轮旧→新，中位 ms |
| --- | ---: | ---: |
| 100，单个相同文本匹配 | 98.17 → 99.90 | 97.99 → 97.60 |
| 1,000，单个相同文本匹配 | 97.39 → 98.30 | 97.03 → 97.00 |
| 5,000，单个相同文本匹配 | 98.44 → 98.39 | 98.42 → 97.26 |
| 5,000，单个语义匹配 | 118.59 → 118.74 | 118.91 → 118.68 |
| 1,000，密集匹配 | 316.32 → 314.88 | 322.17 → 319.05 |
| 5,000，密集匹配 | 325.56 → 319.36 | 330.35 → 322.97 |
| 20,000，密集匹配 | 359.87 → 323.46 | 363.00 → 328.39 |

1,000 条密集匹配仍为配置重复拒绝，5,000／20,000 条仍为容量拒绝。两侧全部保留 128 次 BEGIN／ROLLBACK、相同候选 SQL 和解析次数：相同文本 256 次、语义相同文本不同 384 次。移除的是一次 advisory lookup；候选容量和逐条 writer 没有放宽。不能把少量耗时差异都归因于稳定收益。

独立 Python tracing，两轮 5,000 条密集历史约 1.58 MB→0.40 MB，20,000 条约 5.98 MB→0.40 MB；1,000 条约 0.42→0.40 MB。小／稀疏历史约 0.24 MB，部分新样本增加不足 1 KiB。它们是本夹具实际峰值，不是所有输入的固定内存上限。

独立 SQLite allocator，两轮 5,000 条密集历史约 3.62→2.57 MB，20,000 条约 4.63→2.57 MB；1,000 条约 1.18→1.04 MB。单个匹配仅减少约 5 KiB，绝对峰值仍随数据库页缓存变化。计数定义见 [sqlite3_status64](https://www.sqlite.org/c3ref/status.html) 与 [SQLITE_STATUS_MEMORY_USED](https://www.sqlite.org/c3ref/c_status_malloc_count.html)；不含另行配置的辅助 page cache。Python／SQLite 分配均不是 RSS，不能相加为完整进程预算。主机非独占，普通两轮在本片全量回归启动前完成。
