# 提案去重的临时集合与历史捕获时点

基于 Core `ca5ad4d2c0ec3e8eb2f3ba69ff25cc29c295f399`、Pro `316b9e0b39147462b6e861a2bfb9d23bdff48e04`。研究调用在 provider 之前仍读取并保留全部已有 ID；解析得到完整 JSON 提案批次之后，只把其中可能命中的 ID 放入临时过滤集合，继续使用原来的重复过滤逻辑。

## 范围与边界

新增的私有 helper 服务于研究调用中已经完整构造的 JSON 批次和已有 ID 列表。原通用 `_filter_duplicate_ids` 不变，其他调用仍保留原有可迭代输入行为。保留空 ID 的归一化、已存在项与批内重复项的顺序、原对象身份及重复拒绝理由。没有在 provider 返回后重新查询数据库，也没有引入历史缓存。

该 helper 不承诺有状态自定义 Python 对象或一次性批次迭代器的语义。完整历史读取、列表、读取时用于去重的集合、谱系全表及其他上下文消费者仍然存在。这里只有过滤阶段的额外集合随提案批次收窄，不是完整研究的 I/O、内存或 RSS 上限。

## 基线、时点变化与差异检查

既有定向基线 92 项通过、10.09 秒，之后加入新测试并保留旧实现 4 项通过、1 项成本失败（0.91 秒）。安装候选后，最终定向 97 项通过、10.93 秒。上述源码／测试输入均冻结，没有在存活的验证进程中修改源码或测试。

四个真实研究调用测试覆盖 Markdown／SQLite 来源，以及捕获时已存在／不存在两种情况。provider 在调用期间分别删除已有 ID 或新增原先不存在的 ID，过滤仍按调用前捕获的历史判定。测试只验证研究提案生成与写入；后续 Core 准入仍自行执行当前状态检查。

固定成本测试在新解释器中预先构造 20,000 个历史 ID 和 16 个提案。历史与返回值保持驻留，旧实现过滤峰值 2,622,176 bytes 超过该固定夹具的 128 KiB 阈值。阈值不包含历史获取、谱系或整轮研究。

正式差异比较保存 100 组 JSON 批次的完整保留／重复对象位置，覆盖 0／1／10／1,000／20,000 条历史、0／1／2／16／128 条提案、全新／已有／批内重复／混合输入。另保存一组包含空值、布尔、数字、bytes 等普通内置值的边界比较。新旧输出一致、输入未改变；原型与正式运行均另行保留。

## 实际 HTTP、CPU 与夹具失误

两个正式独立项目各含 5,000 条导入失败历史、20 条导入合格记录及一个已有提案 ID。它们收到完全相同的本地 HTTP 响应 A、B、A、B，分别预先记录 A 或 B。实际过滤拒绝三个重复项，仅另一项进入正常决策合约、源文件准入和 CPU 执行。合约原始容量为四个提案，实际只准入一个。

最终两次 CPU 动作、八次新进程 CLI、两次真实 loopback HTTP 请求验证：已有 A 时执行 B，已有 B 时执行 A。观察器记录 5,021 个完整历史 ID 在 provider 之前捕获，过滤时列表内容相同；输入顺序、保留位置、重复位置均核对。产物内容、执行引用、TREE_CLOSED／ECHILD_WALL、SETTLED 结算、SHA 和四张表的新进程重放关联一致。

前两版夹具错误均保留：v1 错把正确的 `partial` 状态当成 `accepted`，在两次 CLI／一次 HTTP 后失败，尚未启动 CPU；产品已接受一项并按重复理由拒绝三项。v2 完成四次 CLI、一个 CPU 动作及一致重放后，核验误读执行表不存在的 `idea_id` 列，正确列名为 `task_id`。v3 只修正夹具，再从新目录完整运行两个场景。三版产品源码相同，未通过改产品行为迎合夹具。

这些是合成导入历史和确定性本地 provider，不代表模型信息利用、真实科研质量或生产验收。正常 CPU 执行来自新提案，导入历史没有执行科研。许可替身仅在隔离验证进程内。

## 两轮成本与完整读取的限制

下表固定为 16 个提案，行中的历史数为 SQLite 记录数。读取夹具另有一个仅存在 Markdown 的 ID，及最多十个与 SQLite 重叠的 ID；完整捕获为表中数量加一。1／16／128 个提案的全部 24 个范围组合均在原始记录中。

| 100 | capture_and_filter | 0.2605→0.2588 | 0.2652→0.2645 |
| 1000 | filter_only | 0.0404→0.0375 | 0.0407→0.0360 |
| 1000 | capture_and_filter | 0.7132→0.7065 | 0.7169→0.7115 |

20,000 条历史的完整读取再过滤两轮约快 5.9%／5.8%，过滤本身约快 56.5%／59.7%。100 条历史的过滤稍慢，完整读取再过滤近乎持平。普通计时没有覆盖 provider 或真实研究用时，不能外推科研提速。

20,000 条、16 个提案两轮的完整读取再过滤 I/O 中位数新旧均为 rchar 516,674 bytes、syscr 132、read_bytes 0；过滤单独范围均为 rchar 119、syscr 2、read_bytes 0，来自采样辅助读取。本片没有减少源读取。

计时在定向、差异及最终实际项目通过之后进行，两轮普通测量各预热并交替旧／新、新／旧、旧／新；内存另以两个顺序采样。`filter_only` 只测过滤；`capture_and_filter` 包含实际完整 ID 读取后过滤，但省略了真实调用中间的上下文、provider 和谱系步骤，不是完整 cycle。

20,000 条历史、16 个提案的过滤峰值两次均从 2,621,736 降至 2,392 bytes；完整读取再过滤只从 4,135,152 降至 4,113,791 bytes。两种范围的 GC 后存活分别为 216／366 bytes，新旧一致；预先建立并保留的输入不计入这次 tracing 起点。

输入历史、提案和返回值保持驻留，正常运行时与字符串驻留分配保留。较大的完整读取峰值仍然存在；减少一个后续临时集合不等于同等幅度降低整个读取阶段峰值。小规模的回退、GC 后存活及原始 I/O 数值均留在证据中。
