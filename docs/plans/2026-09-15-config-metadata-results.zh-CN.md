# 按实际样本读取研究配置元数据

基于 Core `47f12e295fbe93287328b6278a304877ee898169` 与 Pro `58ab29871b7c2d3121720ee8d144ec32fdf78c2b`。此前研究配置维度分析收到有限的合格页面后，仍把全库配置摘要读入字典。本片先按原主指标顺序选取实际分析样本，再在同一读事务中按 ID 分批查询配置。

## 实现和保留的边界

普通列表、字典记录、字符串 ID、有限数值指标，以及 1–5,000 的普通整数样本上限使用新路径。主指标并列保留原输入顺序；每批最多 128 个 ID，各批共享事务。只有完整读取成功后才产生配置统计，读取失败不会返回部分模式。调用方已有事务时保留其事务和未提交写入；否则只结束本次开启的读事务。

特殊上限、重复入选 ID、自定义行／文本工厂及不匹配的主键结构沿用旧路径。配置 JSON 解析、缺失配置、每值至少三个样本、绝对路径维度整体抑制、组内求和及真正最好／最差端点均保持原规则。配置只提供元数据，指标和资格继续来自当前合格证据；空合格集不恢复缓存成绩，归档检查入口保留。

读取范围有一项明确变化：未入选配置中的非法 UTF-8 不再被解码，因此不会使当前样本的整个统计失败；入选坏字段仍使配置统计失败。没有把这项变化描述成所有异常诊断一致。元数据来自稍后的数据库读取，资格和配置仍不是文件／数据库的原子联合快照。

128 限制的是查询 ID 数量；状态汇总仍会扫描历史，页面元数据总耗时不是固定成本。单个配置字节、维度值、输入证据列表、状态汇总、其他上下文步骤及默认全历史资格核验仍没有本片新增的整体容量上限。没有缓存旧配置或增加执行权。

## 基线与行为验证

既有定向基线 79 项通过，10.44 秒。旧成本检查保留两个预期失败：只需 16 条或 5,000 条配置时，旧实现均物化 5,500 条。新增 21 项测试；最终定向 100 项通过，10.99 秒。首次新测试中，两种日志模式的同均值分组预期顺序写反，出现 2 失败、98 通过；原测试及日志保留，修正预期后通过，产品源码未因此变更。

正式差分保存 33 组完整输出／异常一致结果和 3 组已声明的未入选坏字段范围差异，包含主指标方向／并列、特殊上限、重复 ID、无主键、不同文本工厂和调用方事务。另有四组 DELETE／WAL 并发写入检查，及两组第二批查询失败检查；三页为 128／128／3，读取期间一致，释放后能读取下一代数据。

原型首次探测因把字符串数据库路径直接传给要求 Path 的入口而失败，尚未计时。原型首次边界检查虽然功能断言通过，但末尾连接没有显式关闭，退出时 WAL 检查点改变数据库并删除两个辅助文件；这三个原始清单项没有完整保留。原报告、缺陷说明、原脚本和现存文件均保留，第二版显式关闭连接后重新验证全部数据库文件。原型不是最终性能验收样本。

一次正式计时启动还使用了错误 recorder 路径，在 recorder 启动前退出 2，未产生样本；原错误另存后改用既存正确路径。没有伪造冻结记录或补写原运行报告。

## 实际产品路径

四个独立项目分别组合 research evidence v1／v2 和合格／污染反例；每个项目包含 260 条导入历史。实际研究 CLI 使用 custom HTTP backend，向仅绑定 loopback 的确定性本地 HTTP 服务发送真实提示词并处理响应，两次请求读取两页，每页 16 个候选。

第一页偏好 A。第二页完整合格数据中 B 的均值更低；将三条关键 B 结果标为污染后，只剩 13 条合格记录，偏好变为 A。provider 根据实际提示词中的配置统计生成提案，正常合约、源锁和 ingress 接受后，由真实 CPU worker 执行。最终产物保留选中的变体、来源、观测模式和分数。每个项目再从新进程重放，ideas、attempts、reservations、artifacts 四张表逐字字段相同，没有重复执行或结算。

共四个实际 CPU 动作、16 次 CLI、8 次本地 HTTP 请求。观察器记录每次配置读取为 16／16 或 16／13，查询 ID 与当前页面合格 ID 完全相同；每页 prompt 文件与实际 HTTP 请求、原生 manifest 指纹核对一致。第二页之后仍有未读历史，provider 的停止不代表枚举完成或研究收敛。

本地 provider 是确定性协议夹具，没有真实模型、账号或科研收益验收。许可证替身仅在 Pro 测试子进程中；Core-only 子进程主动禁用 Pro 导入，因此原日志含可选扩展导入诊断。非流式 HTTP 模式为显式配置；既有服务、GPU 和部署未变更。
