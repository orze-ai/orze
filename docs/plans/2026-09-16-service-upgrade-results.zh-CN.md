# 同一作用域内的 CPU 服务运行包切换

已接通显式 `orze service upgrade`：从完整关闭的 CPU 服务及固定备份准备新宿主，使用
当前运行包继续原数据库中的工作，保留旧历史、执行代次和累计预算。
这是原 P2 状态兼容与旧所有者交接的一部分；完整回滚、生产部署和真实研究收益仍未完成。

## 验收的真实版本与边界

旧 Core 使用本片之前实际提交的 `913e7be297e3e9ff93544af9260bee52c0d975d5`，新 Core 使用
本片候选代码。保留的旧包共 294 个文件，已逐字节与该 Git 提交核对；每个产品夹具的旧
运行目录又与此库存比对。Pro 在两端保持本片起点的同一运行包，没有声称验证 Pro 升降级。

两端使用同一解释器、项目配置、工作目录和数据库／results 文件身份，适配
`local_cpu_state_v1` 所核验的现有关闭状态。没有复制出空数据库，没有修改旧配置或重写
历史授权，也没有为迁移关闭项目的 `controller_runtime` 检查。需要配置、解释器、作用域
或数据格式转换的组合仍不属于本次验收。版本号相同或不同本身都不证明状态兼容。

## 授权如何衔接

源包按原登记的目录、内容哈希和文件数直接读取，目标进程不导入它。新读者核验当前
关闭历史，并与已固定备份中的服务、数据库、控制器、关闭证明和运行包匹配。
源服务如果已经恢复过，其自身已完成的交接使用真实历史 CLI／解释器身份核对。

此例外只用于关闭记录的读取。新进程的握手、payload 和 `_Admission` 仍检查当前运行时。
普通 `recover` 仍拒绝用新包直接读取旧服务；产品用例先确认这条拒绝，再执行显式升级。

准备命令只创建一个新服务配置。实际启动时重新核对源包、备份、旧进程缺席、管理单元、
停止标记和结算状态；授予执行权继续使用既有 `controller_handoffs` 唯一源约束与当前
代次事务。并发的新配置文件不是两个授权。新宿主保留其实际创建的进程句柄，旧 PID
只用于缺席检查，不成为进程控制能力。

## 实际产品结果

初始旧服务和已经有一次旧版恢复的服务都完成以下链路：旧版实际执行、关闭、备份，
新版准备并实际执行、关闭，再进行普通恢复。两个动作各保留 60 秒预留，原 120 秒预算
耗尽后第三个动作没有建立 attempt；策略仍返回 `wall_envelope_exhausted`。没有因换版
或重启退还成本。全过程保持源权威记录不变，所有已捕获控制器均确认退出。

专项还覆盖：

- 旧二进制的恢复与新版升级竞争，以及两个升级请求竞争：两者完成源校验后才同时争用，
  最终仅一条授权、一个后续 CPU 动作；另一宿主拒绝。
- 启动前退回旧运行包：旧环境普通恢复成功后，未使用的升级声明过期，之后启动被拒绝。
- `SPAWNING` 已落盘但尚未 GO 时注入 Stop：保留原未消费授权；移除夹具自己的 Stop 后，
  旧版恢复和重复启动仍被拒绝，没有第二次执行。
- 备份损坏、源包变化、关闭记录变化、数据库结构变化、Stop、未知适配器和目标版本
  不匹配：均在新控制器出现前拒绝。

基线保留了两个实际失败：旧包产生并关闭了有效 CPU 状态，但当时没有升级入口。
首轮实现 2 项通过，扩展边界后 12 项通过，最终专项 14 项通过。CephFS 上另有两条实际
升级链通过，配对集成 51 项通过。Pro 全量 1,681 项通过；Core 全量 5,570 项通过、
10 项跳过、2 条既有 pytest 导入重写 warning。最终候选的两仓源码／测试库存一致且
运行前后未变；可选 Pro 许可和未提供的 CephFS 专项父目录仍按原报告跳过。

标准库独立脚本核对专项的 13 个项目、18 个 CPU 动作、22 次控制器出生和 9 条交接授权：
原始 attempt、结算、准确预留、旧／新 CLI 字节、源 session 和代次相互吻合。
同一脚本又独立核对全量回归中的 13 个升级项目，得到相同的动作、出生及授权数量。
独立脚本首版将预留字段误写为 `reserved_ns` 而退出；修正为实际保存的十进制
`reserved_nanoseconds` 后复核通过。原脚本及失败输出均保留，产品源码没有因此修改。
共享存储的两条链路另有 4 个 CPU 动作；这些数字不代表全量测试中的全部执行次数。

## 新增成本

针对同一真实关闭状态，在各自的旧／新解释器导入环境中进行 8 次交替只读检查，得到
完全相同的源关闭证明。计时从依赖导入后开始，不含 Python 启动；不启动宿主或 CPU 动作。

| 检查 | 中位数 |
| --- | --- |
| 旧版同运行包关闭状态检查 | 120.20 ms |
| 新版兼容状态及备份检查 | 239.32 ms |

专项项目中的升级准备命令约 0.57–0.61 秒，中位数约 0.58 秒，包含解释器启动、校验和
新配置发布。这是小备份上的新增功能成本；准入复检会再次读取源包和备份，不能将这些
数字外推为大备份性能保证，更不能作为研究提速。

复制归档；无关全量临时目录保留在本机，全量日志和 JUnit 均保留。

私有 422 个载荷与索引一致，最终源码未变。
