# 从调度产物重算质量：任务核验与真实研究边界

新增 `examples.research_comparison.scheduling` 只读任务核验器和 `audit-scheduling` CLI。它从实际候选文件重算可行性与价值，核对原生尝试、评价产物、观察、关闭与预算结算；不采用模型自报分数。Core／Pro 产品源码及既有测试未修改。

**这完成了一个任务适配器的质量与原生账本部分，没有证明研究能力或等预算产出提高。** 使用的是已经公开的调度任务，不能重新称作独立留出任务。完整两臂身份、模型／工具／环境与初始状态、整个项目覆盖、真实费用及策略使用证据的时间仍未齐全。

## 质量如何来自产物

调用方另行提供固定实例、评价协议、完整预期 attempt Ref、选中评价 Ref 和可选复验 Ref。核验器读取冻结捕获的完整数据库记录、产物字节、受监督控制器调用及前后快照。它不执行捕获的命令，不读取记录中任意路径；SHA 只固定输入字节，不认证记录采集者。

每个原生尝试都必须与其终态、监督绑定、实际结算和产物／观察集合对应。候选生产者须在评价器之前的控制器调用中关闭，来源产物和 effect 身份一致。配置采用与 Core 实际消费者相同的有界 YAML／JSON 解析。评价结果从候选的作业、时间窗、依赖、容量和价值重新计算，逐项核对评价输出与发布观察。同步伪造分数和文件摘要也不能替代实际可行性。

复验表示同一候选在另一个原生评价尝试中再次得到一致有效结论，不表示独立生成了第二个候选。合法零分保留为 valid；无效候选没有分数。不同协议分别统计观察，旧协议的 valid 不能凑够新协议的覆盖门槛。失败评价尝试、无观察尝试与额外协议的结果均保留，不推断全局最优。

## 实际 Pro → CPU 产品检查

两组新隔离项目走真实 Pro research CLI，HTTP 传输采用确定性离线替身。每组接受一个显式调度候选提案，经原 Core 执行生产、评价与独立评价复验，再由新进程重放；每组 3 个、合计 6 个真实 CPU worker。合法候选经历一次离线重试，总计 3 次替身传输、0 次外部模型调用。

| 控制 | 原生执行 | 产物质量 | 复验 | 原生已结算额度 |
| --- | --- | --- | --- | --- |
| 合法调度 | 3 次 completed | valid，价值 30 | confirmed | 6 秒 |
| 重复作业候选 | 3 次 completed | invalid，无分数 | 未确认有效 | 6 秒 |

执行成功不等于科学有效。重放没有新增执行／扣记／产物；任务核验 API 与新进程 CLI 输出一致。独立用量核验同时关联实际 native prompt：合法候选的失败重试用量未知，完整 calls／tokens／USD 保持 null、已知 token 小计为 5；无效候选返回 calls=1、tokens=5，USD 仍未知。这是明确构造的接线控制，不是两个模型或两种研究策略的 A/B 实验。

另一个不导入产品、任务评价器、新核验器或归约器的 stdlib 脚本，用区间边界扫描复算 8 份捕获中的 13 次评价，校验容量、依赖、价值与计量算术，结果一致。这是独立进程机械检查，不是另一位审阅者，也没有新研究执行。

## 保留的真实缺口与修复

1. 缺少新模块时收集失败，属于功能尚不存在，不称作旧产品缺陷。
2. 首版任务核验器假设配置都是 JSON。真实 Pro 提案按合法 YAML 保存，三个 CPU 步骤正常完成后，核验发生 JSONDecodeError。沿用 Core 正式解析器后，新产品链通过；同一份已关闭的 YAML 捕获在保存的旧核验器上仍失败，在修正版上通过。初次失败的数据库和日志保留；该版驱动在核验后才保存整份 capture，因此不宣称找回不存在的完整调用捕获。新版驱动先保存 capture／scope 再核验。
3. 成本测量发现首版读取按 64 MiB 上限申请缓冲区。11 字节输入的 reader 分配峰值约 67.1 MB；约 450 KB 完整 CLI 捕获峰值约 74.5 MB。按已核对的实际文件大小加一字节读取，保留读取后元数据／长度／摘要检查，修复了额外分配。增长、缩短、超限和微小文件分配检查保留。

相同新进程包装器、相同捕获字节，旧／新及新／旧两轮：旧 Python peak 约 74.52 MB，新约 13.00 MB，8 个输出逐字节相同。这是本片新读者草稿之间的开销修复，不能算作既有产品的科研提速。

## 最终完整 CLI 成本

最终读者再次读取相同两份产品捕获；每格 3 次冷进程计时，另一次 tracemalloc，输出仍与原产品 CLI 完全相同。

| 捕获 | 输入 bytes | wall 中位数 ms | 子进程 CPU 中位数 ms | Python peak MB |
| --- | ---: | ---: | ---: | ---: |
| 有效候选 | 453401 | 164.31 | 132.65 | 13.00 |
| 无效候选 | 455153 | 164.20 | 132.71 | 13.00 |

包含导入、读取、解析、原生核验、重算评价、序列化、写出及 fsync。wall 包含父进程等待轮询的离散粒度；共享机器少量样本不支持微小速度差异或普遍保证。Python 分配不等于 RSS。这是额外核验成本；研究全过程的模型、GPU、生产与失败 worker CPU/wall、证据被策略消费的时间仍不能从这些记录补成零。

## 回归范围与交付

既有定向 133 项通过；初版 154、兼容性修复前后 161 项通过。分配修复的旧实现实际 1 失败／3 通过，隔离修复与全部新任务检查 32 项通过；最终实际源码定向 165 项通过，最终配对 31 项通过。

Core 全量 5,306 通过、6 可选跳过；Pro 全量 1,647 通过。**这两次全量早于最后一行读取分配修复及四项新增检查。** 它们运行期间源码始终冻结；句柄明确结束后才合入已验证的单行修复。最终定向覆盖全部任务核验、CLI、原有对照与调度检查，最终 CLI 成本重放同一批真实 Pro 产物。除该新读者一行及新增四项检查，Core 完整输入一致，Pro 源／测试未变；不将修复前全量冒称修复后的全量。

原始失败、JUnit、Git 基线、三个候选快照、原型、真实产物和逐次成本均归档，机械核验逐文件及 SHA／Git blob。公共仓库保存 Core 证据；包含 Pro 库存、实际研究提示与配对原件的材料留在私有仓库。整个 P1／P2／P3 目标继续开放。
