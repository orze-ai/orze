## 不变边界与证明范围

产品 src/schema 继续固定 Core `8f61ae5f68c0846d5149aceb4df55c69263c9df2`，Pro 实现不变；V1-07A 七个应用文件、四个测试及已知领域判据不改。只新增排程 Domain、普通应用登记入口、声明式输入和验收代码。不新增 Policy 实现，也不把取负/魔数 cost 伪装为 maximize 适配。

原挑战不要求沿用 CommonPolicy、不要求求全局最优或自治提出候选。本片采用既有 QueuePolicy 的 `idle=wait` 配置，以及现有公开的普通任务准入 / CLI replicate；测试声明所请求的任务，执行始终由同一真实 CLI/Orze/原生监督器负责。它证明声明式跨领域工作流，不证明 CommonPolicy 无代码迁移，也不替代 A 已单独证明的策略自产分析；不得用此路线倒改 A 的自主提案验收。

新增 Domain 的 producer 输出严格的 `instance_id/schedule` 候选 artifact，明确零 observation。独立 evaluator 只读绑定的原 artifact，从原始 UTF-8/JSON 计算可行性；目标为 `scheduled_value`、方向 `maximize`。有效零分及较低有效分数保留；invalid 给 typed reason 而不携带可排名数值。相同数值只称数值相等。protocol/comparison_scope 分开 v1 与 v2，v2 的唯一语义变化为 capacity=1。

## 计划执行与故障分层

主工作流计划 7 次真实 native action：required-only 确定性 baseline producer → v1 评估 → 按输入稳定次序、最早可行位置的确定性 greedy challenger producer → 同 artifact 的首次 v1 evaluator 在写出部分结果后真实非零退出 → 失败已确认/结算后，用新的 Python controller 和新的显式 task 以完全相同 raw domain_request 从同 artifact 恢复评估 → 同 artifact 的 v2 评估 → 对已完成 v1 evaluator 作公开显式 replicate。

不把新 task 说成接管旧 attempt。失败后的普通同配置新任务准入是现有能力：failed 不占普通去重；原失败 task/request 不重置。故障注入仅影响指定 evaluator 子进程，代码和研究请求不靠改 purpose/seed/config 加盐；故障标志、partial 文件、非零返回码及真实 FAILED/SETTLED/no-observation 都须记录。不得先持久 Stop，再绕过它重启。

另以独立候选分别验证精确 deadline / end-start 正控，以及 duplicate ID、missing prerequisite、resource overload、malformed artifact 四个单故障负控。每个候选使用真实 producer artifact 和正常完成 evaluator；invalid 不是执行 HOLD。其它 schema/type 与独立判据检查由单元测试补充。计划动作数只是预算预估，完成报告必须来自实际身份/账本去重计数，不预填执行结果或最优排程。

使用单 CPU slot、每动作 2 秒 wall envelope，各私有项目声明足够且固定的预算；问题 capacity/demand 不是物理资源。每个执行步骤使用真实独立解释器 CLI；登记、准入和请求调用与真正 worker/action 分别计数。完成所有显式工作后至少三次空闲调度检查只能 Wait，不新增 task/attempt/reservation/observation 或 agent 调用。复验请求精确重放不得再创建或执行副本。

## 证据与保留缺口

保留全部 CLI 命令/退出/PID 与进程边界、实际 worker/attempt/transition、原 artifact 内容哈希、协议/observation 身份、失败前后及重启后权威表快照、partial 文件所在私有 work 目录和逐动作计量；独立 verifier 不复用 Domain 的校验函数。使用实际 v1/v2 数据验证不混榜与旧观察不改写。

只验收 evaluator 子进程的已确认失败后恢复评估。exit 0 但 envelope 不完整的 publication HOLD、控制器丢失 RUNNING owner、提交不确定，以及 TERMINAL/effect 已确认但预算未 settle 的崩溃窗口，仍是另列未完成项，不用成功重评掩盖。

若上述流程实际要求改冻结产品接口，本轮留出不计通过，先登记真实失败和新缺口；不更换挑战、不修改判据以造绿。完成要求仍是实际目标测试、冻结全量/兼容、独立复核及精确提交/远端核对；不证明科研收益、GPU 节约或整个 V1 完成。
