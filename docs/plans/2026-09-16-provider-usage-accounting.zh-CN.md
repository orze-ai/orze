# 研究调用用量：逐次记录与收益结论的边界

## 结论

修复 Pro 中研究调用的计量缺口：缺失用量与明确零分开，失败重试和跨提供方回退逐次保留，拒绝／截断不抹掉已报告用量，非法 token 数不再被强制转成数字。研究请求通过提问清单哈希和原生研究尝试 ID 关联。Core 产品源码、测试和示例未改动。

这增强了研究成本的可观察性，没有证明真实模型研究更快、更省或更强。HTTP 失败的实际用量、提供方账单、工具费用和 GPU 时间仍可能未知；旧 CPU 结果不会因增加日志而成为新研究证据。整个 P1／P2／P3 目标继续开放。

最终定向104项、Core全量5,278通过／6可选跳过、Pro全量1,610、配对31项通过。输入冻结、原始输出、基线Git字节、原件与归档、完整调用成本和CPU重放均已机械核验。这些检查有重叠，不代表独立科研成功次数。

## 确实改变的行为

- 原来无 usage 与明确 0 都写成 0；现在前者是未知，后者保留提供方报告的 0。
- 原来 HTTP 429 后成功，两个传输尝试只记成功一行；现在一个逻辑调用下有两个独立尝试，失败的用量未知，成功的报告值保留。保守 token 预留仍逐次扣记，不退款。
- bool、字符串、负数、过大整数与矛盾字段不会成为可用总量；保留有效原始数字和字段来源供核对。
- Gemini 思考 token、Anthropic 缓存读取／创建、Kimi 缓存字段和 OpenAI 缓存明细按各自语义保留。缓存或推理已经属于原计数的部分不重复加总；没有报告的可选分项不补零。
- 预算拒绝为零次传输；准备后崩溃保持未结束；新进程、新请求和不同逻辑调用不共享调用 ID。
- 计量写入失败、目标替换、部分写入和并发追加不会改变提供方结果或增加重试。日志不能授予执行／恢复权限，也不证明模型版本或账单真实性。

日志升级为 schema 2 事件格式。内置研究角色继续使用原有日志路径，仓库外旧格式读取方需要迁移。最终行的 `prior_writes_succeeded` 只表示此前未观察到写入错误，不证明最后一行已持久化，更不证明整个研究项目的记录完整。日志读取方仍需核对事件序列及独立尝试库存；本片没有交付正式账单读取器。

## 实际流程验证

离线 HTTP 替身接入实际研究 CLI、提示打包、提供方解析和提案写入。一个 429→成功场景记录两次尝试，提案随后经过真实 CPU worker 产生产物、关闭进程树并结算；新进程重放没有重复扣记。拒绝对照保留已报告用量而不生成提案，CPU 动作数为零。

另有并发线程／进程、流中断后重试、显式拒绝／截断、准备后崩溃、日志替换／写入失败、native 清单关联和直接调用上下文复位检查。全部是受控离线数据；没有外部模型、账号、GPU、既有服务或部署操作。

## 开销，不能算作提速

固定旧 Pro 提交与新代码，各场景四对交替 A/B 顺序；每次用新进程测100个完整逻辑调用。传输为无延迟离线替身，重试 sleep 也被替换；表中是每100次调用耗时的中位数，不能外推真实网络／模型时延。

| 场景 | 旧版耗时 | 新版耗时 | 每次新增耗时约值 |
| --- | ---: | ---: | ---: |
| 日志关闭，成功 | 1.236 ms | 1.556 ms | 3.2 μs |
| 日志关闭，一次重试 | 2.303 ms | 2.850 ms | 5.4 μs |
| 日志开启，成功 | 7.279 ms | 431.604 ms | 4.24 ms |
| 日志开启，一次重试 | 8.913 ms | 656.537 ms | 6.48 ms |

开启后成功调用由1行增至4行、重试调用由1行增至6行，并逐事件同步写入。100次成功调用的日志约21.4→217.9 KB，含重试时约21.4→365.0 KB。独立10次调用的 Python 分配峰值从约4.20 MB降至20–21 KB，主要是旧日志写入缓冲不再分配；关闭日志时峰值增加776字节。Python 峰值不是进程 RSS 或全系统内存。

测量在共享工作机上进行，与全量回归有时间重叠。原始样本、所有配对差和额外成本均保留；这是当前环境的有限工程开销测量，不能称为真实科研提效。
