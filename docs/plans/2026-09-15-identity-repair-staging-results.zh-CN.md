# 旧配置身份修补：减少 Python 行集合并记录磁盘代价

旧身份准备原来一次读取所有缺失身份的配置，再保留全部修补元组。现在把同一源查询的结果分批复制到私有临时 SQLite，释放源游标后解析 YAML，最后在主库的一个事务中比较当前文本并写回。5,000 条约 1 KiB 配置的 Python traced peak 从约 7.91 MB 降至 0.47 MB；耗时和写入量增加。本片不声称研究提速或整个过程拥有内存硬上限。

## 行为与边界

源读取、派生和写回的 Python 行集合每批至多 128 条。所有 YAML／哈希派生完成后才启动主库写事务；中途解析失败不发布先前批次，后面的主库写入失败会回滚前面的写入。源读取仍是一份按 rowid 排列的 SELECT 结果；释放源游标后，其他连接可以修改配置。写回仍比较 `idea_id` 与完整当前配置文本，改过的行不能得到旧文本的身份。

调用方已有事务导致 `BEGIN IMMEDIATE` 失败时，函数不会提交或回滚调用方事务。返回值仍是成功派生的修补尝试数，不改为实际受影响行数。非法 YAML、非 mapping 和状态筛选规则保持原样，大于 64 KiB 的旧配置也没有新增拒绝；没有缺失身份时不创建临时文件。

临时目录仅属于当前调用，权限为 0700，正常返回和 Python 异常退出时清理。强制终止进程或主机崩溃可能遗留私有临时文件；下一次调用创建新目录，不读取旧暂存。暂存库沿用 DELETE journal、FULL 同步、normal locking，并将自身 SQLite page cache 配为 512 KiB。主库准入、当前事务去重、原子提交、已有状态和执行授权保持原有职责；暂存不是可复用的资格缓存。

**仍无硬界限：**单条旧配置大小、YAML 展开、临时磁盘总量、总 I/O、全历史返回映射，以及 SQLite 自身的排序与内存。当前源查询仍使用缺失身份索引后临时排序。128 行不是 128 个固定大小对象，Python 测量也不包含完整 RSS 或 SQLite 原生分配。

## 基线、失败与定向验证

- 60 项既有检查在保存的原件和实现上均通过。
- 新的有界源读取检查在原件上失败：旧 `.fetchall()` 触发 `unbounded_legacy_source_read`。原始失败与旧源码保留。
- 首轮新增检查有一个测试 API 调用错误，结果为 1 失败、71 通过；当时测试文件和日志保留，修正后 72 项定向通过，产品源码没有因此改变。
- 验证覆盖超过一个批次的晚期主库写入失败、晚期 YAML／哈希异常、源读取中途 BUSY 后重新复制、已有调用方事务、暂存失败清理，以及无缺失身份路径。
- 并发测试在第一次 YAML 解析时由另一连接修改第 300 行并提交。修补仍解析原查询的旧文本，但比较写回跳过新文本；正常 writer 随后识别新文本的重复提案，下一次修补才赋予新身份。

## 两轮交替时间与写入量

每轮使用独立数据库，旧／新、再新／旧、再旧／新，共三次样本。每次从同一导入元数据数据库复制；准备、复制、打开数据库和最终结果核对均在计时之外。所有旧／新最终数据库逻辑摘要一致。两个普通性能运行先完成，之后才开始本片全量回归；主机仍非独占。

| 缺失行数 | 每条 payload 字符数 | 旧修补中位秒，两轮 | 新修补中位秒，两轮 |
| ---: | ---: | ---: | ---: |
| 100 | 1,024 | 0.0872／0.0882 | 0.1240／0.1197 |
| 1,000 | 1,024 | 0.7636／0.7858 | 0.8702／0.8799 |
| 5,000 | 1,024 | 3.8094／3.8887 | 4.2090／4.2499 |
| 500 | 8,192 | 2.3890／2.4026 | 2.5100／2.5636 |

所有四组均变慢。5,000 行的 `/proc/self/io` 写入字节两轮都约 12.70→34.12 MB；500 条大配置约 8.57→21.86 MB。这是进程计数，不是共享存储实测流量或 fsync 次数。5,000 行暂存数据库在主库写回前约 6.85 MB；500 条大配置约 4.37 MB，这些时点不是磁盘峰值。临时文件随后删除，归档不假装包含已删除的内部暂存库。

另行插桩的主库 writer 区间，每次都是一次 BEGIN／一次 COMMIT。5,000 行的旧／新区间两轮为 102.02→99.67 ms、92.07→99.75 ms，没有稳定锁时收益；500 条大配置为 41.81→43.84 ms、41.42→43.25 ms。区间包含 Python 执行和暂存读取，是独立单次观察，不是耗时分布。已修补的热调用继续返回 0，样本与全部 I/O 计数一并保留。

## 实际 CPU 执行与重启

一个新项目由真实 Core CLI 空初始化，随后导入 1,500 条已完成的 native CPU 元数据，它们没有实际历史执行。直接准入新动作的负对照返回 `proposal_dedup_capacity`。之后通过真实 ingress API 处理新动作及其同配置重复提案：缺失身份从 1,500 条变为零，只接受 `idea-tail`，重复提案保留。

真实 Core CLI 执行该 CPU worker，产物为 `10`；核实 `TREE_CLOSED/ECHILD_WALL`、SETTLED、终态与产物 SHA。第三次新 Core CLI 回放后，四组关键数据库记录和作者源保持一致，没有重复执行、扣记或产物。共一次实际 CPU 执行、三次 CLI；无真实模型、GPU 或生产服务。

含 Pro 完整源／测试清单的配对记录留在私有仓库，公共 [private index](../evidence/2026-09-15-identity-repair-staging-pro-private-index.json)固定私有提交及 Git 对象。机械核验是另一个进程，不是另一位审阅者；它的本片完成状态不代表整个目标完成。产品 harness 的可选 Pro stub 导入 warning／traceback 原样保留；隔离 Core CLI 的实际退出码、worker 终态、结算和产物均核实通过。
