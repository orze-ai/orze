# Sidecar 续页：减少重复载荷读取并保留额外内存成本

本片减少长历史 ingress 续页对已检查 sidecar 前缀的重复读取和 YAML 解析。前缀提示只保存文件身份和首个有效定义的 ID；当前批次仍重新读取内容，并走原有逐条 writer 准入。sidecar 仍是追加来源，不被消费或确认删除。

## 处理方式与范围

一个 controller 进程内，完整读完的前缀文件可以留下身份与 ID 提示。后页跳过提示覆盖的旧记录前，核实 primary source 作用域、PID、目录命名空间和每个前缀文件；收集当前批次后再复核。文件改写、替换、删除、链接变化、目录变化或 primary source 变化会清除提示，重新解析前缀。即使恢复旧 mtime，ctime／文件身份变化仍会使提示失效。

提示不保存 YAML、原始正文、准入结果或执行授权。最多保留 8,192 个文件、32,768 个 ID 和 1 MiB 的 ID UTF-8 字节；达到任一上限后继续新鲜解析。目录名称每个窗口最多 512 个，续页不重新选择已经核实的前缀名称。完整遍历结束后从头读取；新进程不继承提示。

一个文件尚未完全遍历时，不缓存它的已解析前缀，所以同一个大文件中的后页仍须重新读取、解析前面部分。目录窗口仍会枚举目录，整轮用于“首个有效定义优先”的 ID 集合也仍可能随历史增长。这些界限约束提示与名称窗口，不构成整个循环的 I/O 或内存硬上限。

原有 primary 优先、首个有效 sidecar 定义优先、不可变任务准入、当前事务配置去重、源锁和精确 ACK 规则保留。这里没有新增执行权或接管旧任务的能力。

## 基线与边界检查

- 59 项既有检查在原件和首版实现上均通过。
- 新续页读取检查在保存的原件上失败：第二页读取了 257 个 sidecar，而目标是至多当前 128 条加一次 lookahead。首版共 75 项定向检查通过。
- 补查发现两个状态清理缺口：解析异常可能留下未完成批次的提示；直接发布复核没有拒绝 PID 变化。两项失败保留，修复后最终定向 77 项通过。
- 检查包含恢复 mtime 的改写、替换／删除／硬链接／符号链接、目录变化、当前批次读取时前缀变化、重复定义、单文件续页、容量耗尽和新一轮重新读取。原有测试未修改。

## 完整遍历的时间与读取量

两轮最终版本各使用新项目，旧／新版本交替三次。所有数据是已完成的合成元数据；作者标题与数据库标题冲突，因此真实准入必须保留 sidecar，不能通过丢弃冲突记录制造收益。每轮从没有提示开始，第一批和完整遍历分别计时；完整遍历要求旧／新版本返回完全一致的记录、批次数和载荷哈希。每个文件含一个提案。

| Sidecar 数 | 旧首批 ms，两轮 | 新首批 ms，两轮 | 旧完整遍历 s，两轮 | 新完整遍历 s，两轮 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 98.81／103.43 | 101.41／105.71 | 0.095／0.104 | 0.097／0.105 |
| 1,000 | 121.41／125.06 | 120.63／124.51 | 1.674／1.697 | 0.967／0.985 |
| 5,000 | 148.41／139.29 | 120.88／113.37 | 26.947／26.373 | 6.249／5.953 |

独立读取计数中，5,000 条完整遍历仍为 40 个批次：sidecar 载荷读取从 104,879 次降到 5,039 次，约 28.28 MB→1.36 MB；1,000 条为 4,591→1,007 次。多出的 39／7 次是分页 lookahead。数据库及作者源文件保持不变。

**单文件负对照：**把同样 1,000 条提案放在一个文件里，旧／新版本都读取该文件 8 次，总量约 2.16 MB。两轮完整耗时分别为 1.343→1.332 秒、1.363→1.439 秒，没有稳定收益。100 个独立文件也略慢。首版的 5,000 文件结果约 26.05→6.14 秒单独保留，没有覆盖中间实现或把所有测量混成同一版本。

这些是本地 ingress 成本，不是端到端研究收益。测量与隔离回归在同一非独占主机上有重叠；比较保留交替顺序与每次样本，不以绝对耗时推断生产吞吐量。

## 内存代价

另一次完整遍历分别追踪旧／新 Python 分配，每个规模各执行一次；这不是 RSS 或耗时分布。5,000 条下峰值约 6.14→6.23 MB，测量结束时仍分配的内存约 2.89→5.38 MB。新版保留 5,000 个文件身份与 5,000 个 ID，ID 原始 UTF-8 共 75,000 字节；其余包括 Python 对象、正常执行状态与其他分配，不能把差值全解释为 ID 文本大小。

1,000 条下峰值约 0.981→0.968 MB，结束时约 0.312→0.730 MB。最先执行的 100 条样本包含冷路径和导入影响，不用它推断线性增长。时间收益伴随跨页保留的信息增多，完整原始分配记录已保留。

## 实际 CPU 执行与重启

两个新项目分别采用多个文件和单个大文件布局，每组导入 299 条已完成元数据，最后放入一个 CPU action 及同配置重复提案。先用真实空 Core CLI 初始化，再在真实 IdeaLake 上连续调用三次正常 ingress API；前两页没有新准入，第三页接受 `idea-tail`，保留重复提案。

随后各用真实 Core CLI 执行一个 CPU worker，生成 `[1, 3, 5]` 产物，核实 `TREE_CLOSED/ECHILD_WALL`、SETTLED 与终态／产物 SHA。两个新 Core 进程再次回放，数据库四组关键记录和作者源文件完全不变，没有新增执行或扣记。共六次 CLI 启动、两次实际 CPU 执行；历史元数据不冒充既有真实执行，也不声称这些 API 调用等于生产长期 controller 验收。

## 回归与证据

Core 一次最终全量 4,923 通过、7 个可选 Pro 跳过、2 个既有 warning，1,016.92 秒；Pro 全量 1,152 通过，307.94 秒；最终定向 77 项、配对 31 项通过，输入冻结。集合有重叠，不能相加。

最终独立进程机械核验通过，逐项检查 Git 原件、抽取后保持原样的 sidecar 解析语句、冻结运行及失败、24,794 个归档文件、完整覆盖哈希、内存记录、CPU 终态与重放。279 个未修改 Core 源文件、516 个 Core 旧测试文件，以及全部 95 个 Pro 源文件／146 个 Pro 测试文件保持原件。预核验的 `complete: false` 记录保留，最终记录为 `complete: true`；这只是本片核验状态，不是整个产品目标完成。这不是另一位审阅者。源代码／测试完整清单和原始 Core 证据位于[本片目录](../evidence/runs/2026-09-15-sidecar-prefix/)；含 Pro 库存的配对原件留在私有仓库，公共[private index](../evidence/2026-09-15-sidecar-prefix-pro-private-index.json)固定其提交和 Git 对象。

后续入口：非空的新提案仍会触发 `find_admitted_config_hashes` 的旧身份准备。其 lookup 结果不再决定准入，但准备函数仍一次读出全部缺失身份及配置，然后解析、写回。不能直接删除这个步骤，否则超过 1,024 个缺失候选时可能让原本可准入的提案被容量规则挡住。应继续检查分批准备的内存、事务代价及并发配置修改，保留当前 writer 内完整资格和去重规则。
