# 代码演进上下文：同一配置下合并重复资格扫描

代码演进原先先为排名核验完整历史，再为家族统计重新核验一次。
现在在完整配置和数据库作用域一致时，两者共用一次当前资格扫描。
最终版本 5,000 条导入历史的完整上下文耗时约 **4.21–4.25 秒→2.97–2.98 秒**，
减少约 30%，输出逐字一致。这是提示词准备环节的局部收益，不是模型能力或端到端研究收益证明。

## 行为与边界

- 每个候选继续读取当前原件、验证生命周期和资格，并绑定排名所需的来源身份。
  排名保留完整 Objective 前十；家族统计保留原有浮点转换、并列集合顺序及求和顺序。
- 两个消费者的配置必须完整且类型一致，不能用 Python 的 `True == 1` 合并不同资格规则；
  数据库路由也分别核实。原始 CLI 配置只在其项目
  工作目录内补齐等价的默认路径；`_config_path`、显式不同作用域和不兼容 Core API
  继续使用原有两个读取器，不借默认值改变另一份配置的路由。
- 排名扫描的数据库版本见证保持到标签读取结束。期间提交、文件配置变化或调用方
  配置变化使两个结果一同失效；回滚不当作已提交修改。每页读事务仍在资格读取前释放。
- 身份捕获失败时，排名仍拒绝该项；家族统计另行执行原有资格函数，保留两种读取器
  原本不同的资格边界。这种异常路径不保证只调用一次资格函数。
- 没有跨调用缓存。公共全量排名、单独家族统计、决策基线和其他研究消费者仍执行各自
  的必要读取。家族 ID／数值和聚合仍随历史增长，没有新的整轮内存硬上限。

## 完整上下文成本

使用当前真实报告文件和导入完成历史；每组预热后按旧／新、新／旧计时。
三轮使用不同新建夹具，计时与分配采样、产品执行和回归分开。
前两轮对应 candidate-v5，第三轮为最终类型比较修复后的 candidate-v7。
下表为每轮两次普通计时的范围，单位秒。

| 历史／场景 | 第一轮旧→新 | 第二轮旧→新 | 最终版本旧→新 |
| --- | --- | --- | --- |
| 100，正常共享 | 0.0924–0.0928→0.0663–0.0668 | 0.0929–0.0932→0.0671 | 0.0928–0.0930→0.0667–0.0668 |
| 1,000，正常共享 | 0.846–0.848→0.599–0.602 | 0.857–0.859→0.602–0.607 | 0.850–0.854→0.594–0.600 |
| 5,000，正常共享 | 4.198–4.203→2.983–2.991 | 4.242–4.271→2.960–2.963 | 4.213–4.247→2.966–2.982 |
| 100，项目外原始配置回退 | 未测 | 0.0924–0.0926→0.0932–0.0933 | 未重测 |
| 5,000，仅一条合格 | 未测 | 4.119–4.123→2.861–2.866 | 未重测 |

第二轮脚本保留的总说明沿用“项目工作目录”措辞；`external-cwd` 行实际使用独立外部目录，
以显式 mode、代码和原始记录为准，不把它误算成共享路径。

正常共享时资格调用为 N 次，原先为 2N 次；回退对照仍为 2N 次，且略慢。
5,000 条密集历史最终版本 `syscr` 为 91,903→61,398，`rchar` 约 7.24→4.82 MB。
测得的 `read_bytes` 为零，说明本机预热后的缓存行为，不能解释为没有文件读取。
共享主机上的这些样本不是通用延迟保证。

内存没有改善结论。5,000 条密集历史 Python traced peak 旧约 2.884 MB，新约 2.894 MB；
100 条第二轮新样本为 2.479／2.121 MB，旧样本约 2.105 MB。第一份新样本的结束保留
分配约 1.36 MB，明显高于另一些样本。所有运行时分配均保留，没有从峰值中扣除；
这些是 Python 分配采样，不是 RSS 或完整进程内存预算。

## 产品链与失败记录

两个项目各导入 260 条历史，正常演进 CLI 调用本地确定性可执行 provider。
合格末页最佳项被选为第 259 项；将它标为不合格后，实际提示、提案和 CPU 产物改为
第 258 项。两个 CPU worker 均关闭并结算，新进程重放没有增加执行或扣记。
每个演进上下文实际进入共享路径，带身份资格调用均为 260 次，生命周期页最多 128 个 ID。
决策基线的独立扫描不包含在这个上下文计数内。

provider 知道公开夹具，历史是导入元数据。两次 CPU 执行验证实际调用和恢复，不能
冒充新旧模型研究对照。真实模型、账户、GPU 和已有服务均未调用。

保留了基线对 260 条历史核验 520 次、首版漏掉调用方扫描中配置修改、后续原型错误覆盖
`_config_path` 路由等失败。类型探针又发现：布尔值与数字被当成同一规则时，会错误保留
三条证据；扫描前不一致、调用方中途变化、文件中途变化三个回归先失败，再由严格类型比较修复。
首版类型探针缺少报告列声明，不能证明实际排名错误纳入；修正夹具的 v2 探针先验证三条
独立合格证据，才复现真实错误。两个版本和原始输出均保留。

最终 Pro 相关 133 项、配对 31 项、修正后的类型探针和两个实际 CPU 产品项目通过。
Core 生命周期／标签／报告相关 106 项在相同 Core 源码上通过，运行早于最后的 Pro 类型修复。
最终 candidate-v7 的 Pro 全量 **1,676 项通过**（约 310 秒），与最终定向、配对、
类型探针、产品和普通成本测量使用相同冻结输入。早期 candidate-v5 全量 1,673 项也通过，
但它未涵盖后来发现的三项类型缺口，不能替代最终回归。
本片 Core 产品源码没有修改，未重新运行 Core 全量。

实际服务与生产验收仍开放，原 P1／P2／P3 目标没有缩减。
