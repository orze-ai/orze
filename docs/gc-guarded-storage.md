# 在不支持原子不覆盖重命名的存储上使用 GC

项目可显式选择 `guarded` 清理模式。它支持删除检查点目录、删除可丢弃结果文件，以及
归档结果文件／`overlays` 目录。当前 CephFS 隔离验证已走通这些操作。

```yaml
gc:
  enabled: true
  checkpoints_dir: checkpoints
  storage_mode: guarded
```

先使用既有 GC 入口检查候选：

```sh
python -m orze.agents.orze_gc --config /absolute/project/orze.yaml --dry-run
```

检查后，移除 `--dry-run` 执行；`--gc-results` 和 `--archive-dir` 仍使用同一配置。
默认 `storage_mode: atomic` 保留原有原子隔离方式。存储模式是显式选择，系统不会
根据文件系统名字跳过检查，也不会在重命名失败后悄悄改为可覆盖操作。

## 为什么需要另一种模式

当前本地 CephFS 对目标不存在时的 `RENAME_NOREPLACE` 返回 `EINVAL`。
[Linux v5.15 的 Ceph 实现](https://github.com/torvalds/linux/blob/v5.15/fs/ceph/dir.c#L1132)
也拒绝非零重命名标志。普通重命名可覆盖目标，不能直接替换原有不覆盖操作。

`guarded` 不移动整棵目录。它在原有短任务事务锁内重新确认清理权限，记录该任务进入
清理阶段，然后释放短锁。未完成的清理记录阻止新的任务写入和认领；大文件 I/O 在短锁
之外进行。清理完成后发布对应完成记录，后续操作继续遵守原有任务状态规则。

归档先用独占创建方式复制所有文件，分块读回并核对哈希、文件身份和同步结果；确认后
才删除源文件。已有目标、符号链接、额外硬链接、目录替换或文件变化会阻止完成。
不会覆盖碰撞目标，也不会复制后删除跨设备的源数据。

## 使用代价

- 归档需要复制和校验全部内容，比同设备的原子重命名慢；在删除源文件前，需要同时
  容纳源与目标两份数据。删除检查点无需制作内容副本。
- 正在清理的任务暂不能开始新的受控写入。其他任务使用自己的事务锁和清理记录。
- 归档保存文件内容和目录结构，创建新的 inode，文件／目录权限分别为 `0600`／`0700`。
  它不提供完整文件系统元数据备份、原位迁移或自动恢复。
- 清理记录沿用有界历史设计，每任务最多 1,024 条；达到上限或历史不完整时拒绝继续。
  已有清理历史的任务在后续准入时需要读取这些记录，具体代价见结果文档。
- 单次流式读写块最多 1 MiB；整棵树仍遵守既有 16,384 条目和深度限制。

## 中断和错误

配置声明的源码、评价文件、已接受产物、保留任务、正在运行或状态未知的任务仍被保留。
停止标记以及注册控制器的 Stop/HOLD 阻止继续操作。

复制、删除或同步中途失败时，不报告成功，不自动撤销或再次执行。原目录可能部分删除，
归档目标可能只复制了一部分；任务的待完成清理记录和 GC 记录均保留，阻止再次认领。
即使源目录已经消失，下一次 GC 仍检查未完成记录。需要核实原件与副作用后再制定恢复
方案；删除清理记录或锁目录不是本功能提供的恢复方法。

所有写入方必须使用理解这些清理记录的同一套已验证运行包。混合运行不识别新记录的
旧二进制不在本次验证范围内。逐次身份检查不等于对同 UID 任意恶意修改提供原子隔离。

## 范围

该模式只解决 GC 对重命名原语的依赖。角色释放仍使用原有协议及原子重命名预检，
因此不能据此宣布完整 CephFS 角色支持或生产上线。它不改变 CPU 动作预算，也不证明
研究质量或效率提升。实际服务、跨机器并发、备份回滚仍需独立完成。
