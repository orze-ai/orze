## 直接影响研究的发现

第二轮发出前已有两个方法完成，原始角色日志明确记录 `authoritative_lifecycle_scan_changed`。构建上下文时另一数据库连接提交了更新，排名一致性检查因此丢弃本次扫描。实际付费提示没有 Leaderboard，也没有这两个方法的开发分数和诊断结果，只有历史状态、可运行源码及谱系提示。不能把报告文件存在当作模型已收到证据。

第三个首批方法在第二轮请求之后才完成，它的开发错误率又恰好等于规则中的共同基线，因此不能按字符串出现次数把它算作反馈成功或缺失。后验核验首次误假定首批三个分数都应缺失，已按原始完成时间与请求时间改正；冻结请求和实验未修改。

## 最小产品修复

Core 保持完整扫描一致性检查，只把同一路径、同一结构、同一进程下的数据库数据版本变化标记为可重新读取。Pro 默认研究上下文收到这种变化后，丢弃整个临时排名，从当前生命周期和原始产物重新核验一次；第二次仍变化则保持无排名。结构、路径、缺失 API 和无效产物等错误不重试，不读缓存分数兜底，不追加模型调用。

没有增加新的角色或评审步骤。旧 Core 没有这一标记时，Pro 保持原先拒绝不一致排名的行为。完整性保护没有被省略，已撤回的方法不会因第一次扫描曾看到它而进入最终提示。

使用闭合后的六个真实方法产物和数据库副本注入一次并发提交，调用完整 `build_context`：

| 提示构建 | 排名 | 实测分数 | 实验发现 |
|---|---|---:|---|
| 原 Pro 实现 | 无 | 0/6 | 无对应反例 |
| 修复实现 | 有 | 6/6 | 包含交叉验证与开发集不一致的测量 |

此复现不改原数据库、不发模型请求、不运行 GPU。它验证反馈送达修复，不是历史第二轮的精确重建，也不证明模型据此更快解题；两个单次上下文构建时间不可当作研究加速统计。

验证覆盖：Core 54 项、Pro 91 项相关检查通过。包括真实 SQLite 数据提交后重新读取、被撤回的首名不可恢复、产物修改后重新评分、字典形态 findings 进入提示、两次变化后仍无排名、路径/结构变化不重试，以及原始排序和证据策略。首次测试命令未加载 Pro 激活环境导致四个收集错误；首次持续变化测试的第二次写入值相同，SQLite 实际未产生新版本，改为不同值后测试通过。这些是测试准备错误，未改动生产许可检查。

共同参考为先前已经观察过的 TREC 开发集，126/817 错误。六个真实模型方法的独立开发评分：

12 份数值预测由宿主独立重算，每个方法保存后重载预测完全一致。最好方法相对基线开发错误率下降 5.56%；没有确认或最终审计，不能称为研究目标交付。第二轮最佳仍是参数/混合权重选择，不能据六个可执行提案宣称创造力提升。

首个字符特征方法的内部组交叉验证准确率从 83.49% 升至 84.57%，实际开发却从 126 错变成 127 错，构成需要传回研究者的反例。SVM 校准内层不是按组的嵌套验证；返回 findings 是模型程序的实测输出及自述，产物来源核验不等于所有科学解释成立。

自然运行未插入显式触发，配置 cooldown 900 秒但原生低积压规则会提前启动第二轮。原诊断控制器总时长 398.48 秒，模型调用约 100.57 / 108.69 秒；不能把 cooldown 配置误解为实际强制等待 900 秒，也不能把本轮总时长当平均达标时间。
