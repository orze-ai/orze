## 原因和必要修复

EMNIST control 的第二轮回执已经记录三个新提案，但原生控制器尚未将它们录入数据库。适配器以“模型回执数达到上限，数据库无待执行行”为完成条件，提前开始最终审计。原生控制器随后正常接纳并启动下一方法，训练和审计在同一 GPU 上重叠约 3.46 秒；执行器的空闲检查拒绝继续。错误在对照适配器，不能据此评价研究策略。

修复只复用已有回执：逐一匹配 accepted_ids、来源文件与数据库，要求所有获准提案都已入库并处于终态，且读取期间回执和来源没有变化，再暂停后续启动并执行最终审计。既不新增调度服务，也不放宽设备所有权或隔离检查。真实故障回执的回归检查证明，旧判断可在第二批三个 ID 尚未入库时通过，新判断拒绝该状态和排队中状态。

另一个协议偏差是角色时限。实际工作项目设定 role_stall_minutes=20、研究角色 timeout=600；中止试验遗漏全局停滞值而继承 5 分钟，并把角色超时改成 1100 秒。后续双方须使用实际的 600 秒和 20 分钟设置。此次固定响应测试仅证明预算末验收时序，没有验证真实提供方的超时行为。

## 双 GPU 修复检查

- 第一版固定响应未为成熟批次提供必要的已评分父节点，原生谱系规则拒绝后续提案。该检查中止并保留，不算完整通过，也不修改谱系规则绕过限制。
- 第二版只从原生提示的 eligible parent IDs 中选择固定样例的父节点。Slurm 1325563 及两步均 COMPLETED/0，两个原生控制器各有 6 个 COMPLETE 方法。
- 8 次本地固定响应、12 次训练和 2 次审计闭合；14 份预测由宿主独立计算，MSE 为 0.9025，相对参考只改善 9.75%，低于 10% 门槛，两组正确拒绝验收。没有提前确认。
- 每个 GPU 上所有训练/审计区间均不重叠，审计晚于全部六次训练闭合；两个物理 GPU UUID 不同，CPU 集不相交，12 GiB 内存上限、只读根目录、PID/网络隔离和无凭证检查通过。
- 10 项故障回归及验收单元检查通过。固定样例新增模型 API 请求 0、科学验收 0，不能当作研究能力提升。
