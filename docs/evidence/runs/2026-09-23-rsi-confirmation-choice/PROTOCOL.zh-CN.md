## 假设与准确干预

当前流程会把一次确认用在最先达到开发门槛的方法上。候选先完成首批两个分支，再用同样的开发指标选择其中最佳方法。后续仍按现有两分支、深度三、最多六次请求探索；若首批没有达到门槛，后续首次达标仍可确认。确认失败后继续研究，不能立即放弃；最终审计仍只有一次。

`confirmation.py::select_confirmation` 只接受开发损失和执行侧状态，返回候选 action ID。它不执行模型、确认或审计，不接触隐藏标签，也不创建预算。失效、未准入和 analysis-only 提案以 `None` 记录为已结束；不能因没有分数而永远等首批。完全相同的开发损失保留先观察到的方法。

运行器把返回 ID 绑定到该方法自身的源码和检查点，在调用确认之前消耗一次确认额度，失败或超时也不能恢复额度。选中第一份方法时，不能误用刚执行的第二份检查点；确认反馈写回被测方法所在分支。它尚未执行真实付费研究，也未接入产品默认。

每次评估先保留 `evaluated-outcome.json` 和带序号/时间的 `evaluation-finished.json`，确认选择另记原始开发损失快照。该批确认反馈完整后、下一批模型上下文生成前，才一次性写定 `outcome.json`；提前交付则在在途请求结算后写定。这样既不改写旧记录，也不会把第一份方法的确认反馈挂到第二分支。核验器按选择前实际已完成记录重算应选方法，并核对源码、检查点挂载、反馈分支、一次确认和两组初始提示一致性。

## 拟定开发筛选

- 两组均使用明确模型 ID `claude-opus-5-5`，相同 high effort、输出/源码上限、提示、ParallelRefine、两并发准备及串行评估。唯一差异为首次确认的选择时机。
- 拟用已经观察过的 KMNIST、Abalone、TREC 和生成 TSP-320，各两个既有划分，每划分两组，共 16 次研究。这覆盖潜在选择收益、现有快速成功、依赖后续探索以及追加昂贵执行的代价。
- 这是已观察任务上的开发筛选，使用旧最终划分也只能称开发证据；不能将它冒充新前瞻验收。旧轨迹不能直接复用成新策略的结果，双方必须重新提出并真实执行方法。
- 保留原共同参考、数据隔离、10%/2% 目标、一次确认和一次最终审计、真实任务 900/600 秒、优化 1800 秒执行限时，以及 7200 秒完整研究限时。所有未达标按 7200 秒计分。
- 每任务固定一对 GPU，第二次重复交换两组 GPU。启动前冻结任务顺序、输入/代码哈希、全部提示和同一资源配置；不因运行结果改变它们。
- 每实例拟上限 $10，整池 $160；这只是待分配上限，**尚未预留或花费**。旧池完整结算后须先核对最新累计账本、保留未知请求，再分配；不重复释放历史余额，不突破用户总上限 $5000。
- 开发推进条件：完整核验、请求用量已知、四任务等权平均验收达标时间降低至少 30%、各任务观察成功率不下降。即使满足，也只支持进入新的前瞻验证；产品默认仍须满足原跨领域、至少 3/4 领域更快、配对区间及真实入口集成等完整条件。
- 本开发比较只隔离确认时机，不证明相对产品当前模型配置的收益。若进入新前瞻验证，须把模型与确认规则作为完整候选，和核对过实际入口的现有方案比较；不能把组合收益单独归因于确认策略。
- 若开发筛选不满足，保留失败和追加执行成本，不改门槛、不删掉不利任务，也不把静态规则或离线测试通过算成研究加速。
