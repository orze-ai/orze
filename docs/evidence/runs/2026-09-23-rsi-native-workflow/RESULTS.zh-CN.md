# 原生研究反馈验证与 JSON 代理兼容修复

本次修复一个会丢失完整研究回答、引发重复请求的客户端问题，并验证真实 Sonnet 提案经过原生接纳、独立执行和下一轮反馈。**没有证明研究效率提高 30%，没有改变研究策略或模型默认。**

## 实际修复

项目 `roles.research` 使用 `mode: research / backend: custom / model: sonnet`。其订阅代理收到流式请求仍返回 `application/json`，用空白心跳保持连接。当前客户端默认期待 SSE；旧代码忽略完整 JSON，最终因缺少 `[DONE]` 报截断并重试。当前进程、项目 `.env` 和该 role 的显式 env 均没有设置 `ORZE_OPENAI_STREAM`；此检查不推断历史进程环境或历史失败数量。

Pro 客户端现在按响应的 `Content-Type` 处理显式 JSON，一次读取完整回答后复用现有终止状态和用量处理。SSE 仍须满足 `[DONE]`；JSON 的截断、拒绝、错误和矛盾终止状态仍不能当作完成提案。现有代理和服务没有修改或重启。

51 项相关检查通过，包含真实本机 HTTP 空白心跳、JSON 完成/截断/拒绝/错误/损坏/非对象/矛盾状态，以及既有 SSE、重试、提案发布和用量路径。`client-checks.json` 绑定生产代码与测试哈希。

## 先离线验证，再两轮真实提案

离线失败全部保留：

1. `offline`：诊断脚本把未经过 `load_project_config` 的配置直接传给命令构造器，缺少 `_env_ORZE_RESULTS_DIR`；在请求前失败。
2. `offline-v2`：本机 fixture 返回完整 JSON，旧客户端把它当作截断 SSE，发出两次本机请求后失败；没有付费请求。
3. `offline-v3`：fixture 正确返回 SSE 后，完整原生执行和反馈通过。
4. `offline-v4-json`：客户端修复后，同类 JSON fixture 通过。两次请求分别属于两轮研究，不是同一轮重试。

真实验证在已经观察过的 TREC-0 开发任务上运行两轮，使用 `build_research_cmd → research.py → run_research_cycle → call_llm`，原生提案入队，再由 Core CPU action 调用受信任的协调程序。研究源码和模型序列化仅在隔离容器内执行/加载；宿主独立计算开发损失，另一个容器验证保存后重载预测完全一致。下一轮实际原生提示包含上一轮源码身份和测量。

## 独立核验与限制

`verification-native-closed.json` 复核冻结源码哈希、模型返回身份、全部用量、实际子进程闭合、4 份预测、容器挂载和下一轮提示。

- 5 个原生进程树闭合，2 次 CLI 调用和 4 个 worker 容器闭合，无在途请求。
- 主模型确认为 `claude-sonnet-5`，两次均有 Haiku 辅助用量。CLI 聚合记录不能用于声称只有两次供应商请求。主模型使用量通过正常 JSON 响应进入原生统计；额外辅助用量另计入总费用账本。
- 临时自有代理保留订阅认证和 JSON 心跳行为，并添加有限次调用、JSON 输出、明确用量和禁用工具/MCP/hooks。它没有替换已安装代理。
- 两轮各生成一个提案，没有 900 秒 cooldown；原项目是每轮三个提案并带 cooldown。两次直接原生 CLI 调用没有覆盖 `run_role_step` 的角色生命周期，不能冒充完整 incumbent 研究效率对照。
- Core CPU queue 不分配 GPU；本诊断的受信任 action 显式把隔离 worker 指向 GPU 2。文本算法主要使用 CPU，不能据此声称 GPU 高利用率。
- 任务已经被观察，仅使用训练/开发；没有读取最终标签，没有新的前瞻能力证据。
