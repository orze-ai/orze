# 下一候选：固定资源下的研究模型互补

这是开发对照的设计草案，尚未分配预算、冻结或启动；不能据此声称平台能力已提升。

## 为什么转向这里

完整源码评审存在三个不同问题：输出截断、换序不稳定、两方法都达标时偏好更慢的方法。增加评审 token 只能针对第一个问题。TREC 的正确首选也没有识别另一方法真实发生的 API 缺陷。因此不先扩建评审树或重跑同一评审。

`model-complementarity.json` 保留此前前瞻试验全部 16 个配对：Opus 5 在 3 对更快、5.5 在 11 对更快、2 对均失败。事后选两者最优可以显示互补空间，但使用了最终验收结果和两条完整轨迹，不能当作在线策略、资源匹配试验或未来加速预测。

[RSIAgent §3](https://arxiv.org/html/2609.15364v1) 的启发是通过有区分度的实际探索获得互补经验，并以环境反馈核验；论文没有证明下面的混合分支方案。[SIFT §4](https://arxiv.org/html/2609.19526v1) 的源码排序也不能代替本地真实执行证据。

## 最小干预

- control：两条分支都用 Opus 5，与已完成前瞻对照的 control 保持一致。它是明确的实验比较对象，尚不能代表所有项目的原生自定义模型入口。
- candidate：一条分支用 Opus 5，另一条用 Opus 5.5；固定整条分支的模型，第二次重复交换分支编号与模型的对应关系。
- 两组均使用原 ParallelRefine、两分支各三步、最多六次请求、high effort、32768 输出上限、相同提示和原有反馈上下文。既不增设评审，也不同时加入 inquiry 或延迟确认。
- 原执行顺序、一次确认/最终审计、失败后继续探索的规则保持一致；不同时运行两条完整研究轨迹再按审计结果择优，不增加验收机会。
- 同样的每实例 GPU/CPU/内存、7200 秒截止时间、请求上限与费用上限；同任务同时对照，第二重复交换 GPU。模型生成的新方法必须真实执行，不用旧轨迹重放推定结果。

## 先做开发筛选，再检验迁移

拟使用已经观察的 KMNIST、Abalone、TREC、生成 TSP-320，各两次重复、两组共 16 次。完整保留共同参考、数据及验收门槛，不把这些任务重新称为未见任务。原源码评审须先全部闭合、核验、结算，之后才能分配新池并启动。旧冻结实验不变。

开发晋级要求：平均最终验收达标时间至少降低 30%，至少三个任务类更快，每类成功数不下降，全 16 次闭合、用量已知、独立核验有效。失败计 7200 秒，报告所有失败、未准入和未用付费提案；不能只计算成功者。运行前须把模型映射、调用收据核验、资源与完整预算链落实到可执行协议并冻结。

开发结果即使通过，也仍需新任务上的四领域前瞻对照和原配对不确定性门槛。实际研究入口与 incumbent 的绑定、经过该入口的运行验证及默认集成仍是原 30% 平台目标的一部分。不会只改 Anthropic 通用回退值就宣布交付。
