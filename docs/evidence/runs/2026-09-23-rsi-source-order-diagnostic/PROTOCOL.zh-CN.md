# 完整源码选择诊断：草稿，尚未发请求

前一确认选择开发对照已 16/16 完成并核验、结算。平均时间只改善 6.7164%，不晋级。下一问题是：不先执行全部方法，模型能否从完整源码中优先识别实际可执行、具有泛化依据且较快达标的方案？

本目录只准备输入。`plan.json` 为 draft；未分配新预算，未请求模型，未启动容器。须完成真实请求准入、核验、资源和评分冻结后才能运行。不是新监控、服务或产品默认。

## 固定输入与盲评边界

- 使用上一轮 candidate 组首批的全部八对源码：KMNIST、Abalone、TREC、生成 TSP-320，各两次重复；不按成败或分数筛选。选这一完整集合是因为该组原本执行了首批两份，能够复用已有检查点而不重新训练。
- 每对分别按 A/B 与 B/A 展示，共 16 次计划评审。两次调用独立，没有先前评审结果或对话记忆；保留顺序不一致与 tie，不能挑更有利的顺序。
- 输入仅有当时可见的任务契约、资源/软件版本、共同参考与开发分数、调用接口源码和两份完整方法源码。不给候选执行结果、候选开发损失、确认/审计结果、隐藏标签或按结果撰写的评价。
- 初始提案只引用共同参考作为 parent；本诊断不评后续迭代方法，避免隐藏不同父模型训练历史后误比代码。
- 评审暂定同一明确模型 Opus 5.5、high effort、4096 输出 token，无重试/后备；只返回 A/B/tie、具体理由和不确定性。理由不能当作真实测量。

## 拟定测量，不改写旧研究

先关闭并保存全部评审，再在独立目录内对全部已有有效初始检查点做特征限定预测，使用相同资源和固定审计数据；原执行失败而没有检查点的方法仍保留为失败，不修复或重训。预计有 15 份有效检查点和一份原执行失败，实际字节及清单必须在新请求前核实冻结。原始实验和其最终统计保持不变。

这是已经观察任务上的事后开发诊断：可以测量偏好顺序稳定性、是否优先选中独立达标方法及对应计算成本，不能重建改变执行顺序后的探索轨迹、模型等待或最终达标墙钟时间。重新预测可能因按时间预算运行而产生差异，必须保留，不择优挑原预测或重测预测。

拟定比较采用：优先比较方法的独立验收资格；两者都合格时，再比较原开发执行加本诊断预测的计算时间。两者都失败不能算有意义的能力排序胜利。源码评审时长、未知用量、解析失败、无检查点、未使用提案分别记录。此指标是选择诊断，**不是平台研究达标时间**。

最终晋级规则需在评审前完整冻结。至少要求展示顺序足够稳定、相对原先执行顺序没有观察到验收资格退步，并在有真实可比标签的案例上提供方向一致的选择信号；样本不足或指标冲突时不晋级。不得在看到评审/补充预测后调整规则。即使诊断通过，也只支持新的真实在线开发对照；原跨领域 30%、新任务、配对不确定性与实际入口集成要求不变。

## 文献与简化

[SIFT 第 4.2–4.3 节](https://arxiv.org/html/2609.19526v1) 使用完整源码提供相对排序信号，仍需要真实评估，其大部分加速还来自异步执行。这里先检验最小的两方法选择，不复制 Bradley–Terry、整棵树或多级评审。论文中代理程序排序的结果不能直接推出研究方法排序有效。

[RRSI 第 3 节](https://arxiv.org/html/2609.24972v1) 强调可归因改动、保留已失败机制及后续迁移。本诊断保留“比较越多不一定越快”的负证据，使用已有源码与检查点降低验证成本；不把事后挑选推广成通用能力。
