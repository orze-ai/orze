# 研究模型开发筛选：优先提高真实解题成功率

旧跨领域 control 的总计分时间为 56,577.06 秒，其中已成功的九次仅占 6,177.06 秒。若成功/失败状态不变，把全部成功时间降至零最多也仅改善 10.91797%。这是旧任务集上的算术上界，不是新任务的收益预测；它说明仅加调度机制不足以解释本轮 30% 目标，必须关注能否解决原来未解决的研究问题。

SIFT 的异步评估不能直接计为 orze 新收益，因为本平台已有批次内并行准备；论文的较强评审模型也不等于本平台值得增加评审调用。先做更简单的能力筛选：保持研究流程不变，只替换真正提出方法和诊断的模型。

## 完整固定设计

- 三个已观察的开发任务：Fashion-MNIST-0、采用修复后私有组/行划分的 Newsgroups-0、Power Plant-0。各模型各运行一次，共九次。它们不是新前瞻验证任务；六个新数据集继续保留。
- 三组模型：control 为 `claude-opus-5`；opus55 为 `claude-opus-5-5`；fable 为 `claude-fable-5-1`。只读 Models API 已分别返回所请求 ID；无生成式连通性探针。
- 每组同样 high effort、32768 输出 token、相同完整提示和 API、相同参考/数据/验收、两条 ParallelRefine 路径、每条三步、最多六次提案。没有共享分支证据、pilot、额外评审或错误画像，避免把多个改动混作模型效果。
- 同样明确呈现已经存在的训练组 ID。确认与审计标签不提供给研究模型。参考只由原开发集选择，复用原始参考 checkpoint，不复用历史研究胜出方法，也不给模型旧研究结论。
- 每次研究仍需 MSE/分类错误相对参考下降至少 10%，且配对分组 bootstrap 差值 97.5% 上界为负。开发改善不能冒充验收。一次确认、一次最终审计，拒绝后不再根据审计结果改方法。
- 从实例开始到独立验收计墙钟，包含哈希核对、模型等待、执行、评分；失败或超过两小时均计 7200 秒。交付与全部请求结算分别记录。无自动重试或模型后备。
- 每容器最多 2 CPU、12 GiB RAM、约 6 GiB PyTorch 显存；训练/分析 900 秒，整批独立预测 600 秒。数据与模型只读，程序和 pickle 只在受限离线容器执行。
- 模型匹配的 Fashion 三组分配 GPU 0/1/2，随后 Power Plant 轮换至 1/2/0；Newsgroups 三组分配 GPU 3/4/5。GPU 6/7 上独立校准不受干扰。共享 GPU 的其他作业保持运行，记录遥测。
